각 항목은 갈림길이 있었던 지점이다. 몇 달 뒤에 "이걸 왜 이렇게 짰지"에
답할 수 있도록 남긴다.

### 프로덕션은 Vercel, GSMSV는 백업·모니터링 노드로 시작

**상황**
교내 IaaS인 GSMSV를 쓰고 싶었다. 그런데 일반 사용자 VM은 `http://ssh.gsmsv.site:<포트>`로
평문 HTTP 접속만 제공한다. Google OAuth는 redirect URI에 `http://`를 localhost에서만
허용하므로 Google 로그인이 등록 단계에서 막힌다. PWA의 Service Worker도 secure context를
요구하고, 세션 쿠키에 `Secure` 플래그를 붙일 수 없어 교내망에서 세션 탈취가 가능하다.
추가로 일반 사용자 VM은 생성 30일 뒤 자동 삭제되며 복구가 불가능하다.

**선택지**
1. GSMSV에 바로 배포
2. Public IP 신청 후 GSMSV 배포 — 전체 7개 한정, 관리자 배정
3. Vercel로 시작하고 나중에 이관

**선택**
3번. 프로덕션은 Vercel + Neon, GSMSV는 2주차부터 백업·모니터링 노드로 사용.
PROJECT_OWNER 승인 후 이관을 별도 과제로 진행.

**이유**
1주차 목표가 "실제 URL에서 로그인이 된다"인데, 여기에 VM 세팅·Docker·Postgres·터널·
배포 파이프라인을 얹으면 일정이 3배가 된다. 그리고 VM을 만드는 순간 30일 시계가
돌기 시작해서, 세팅에 2주를 쓰면 절반을 태우게 된다.

**대가**
서버 운영 경험이 뒤로 밀린다. 이를 보완하기 위해 백업 노드(pg_dump + systemd timer +
SSH 키 + 방화벽)를 2주차에 먼저 붙인다. 서비스가 죽지 않으면서 같은 경험을 얻는다.

### HTTPS는 Cloudflare Tunnel로 해결 (이관 시점)

**상황**
GSMSV는 NAT 뒤에 있고 Public IP는 한정 자원이다. 도메인을 직접 연결하려면
Public IP가 필요하다고 안내되어 있다.

**선택지**
1. Public IP 신청 대기
2. Let's Encrypt를 VM에 직접 설치 — DNS를 제어하지 않아 HTTP-01 챌린지 불가
3. Cloudflare Tunnel

**선택**
3번.

**이유**
`cloudflared`가 아웃바운드로 Cloudflare에 연결하므로 인바운드 포트도 Public IP도
필요 없다. Cloudflare가 도메인의 HTTPS를 종단하므로 인증서 갱신도 자동이다.
앱은 `localhost:3000`에만 떠 있으면 되어 공격 표면이 오히려 줄어든다.

**대가**
Cloudflare에 의존이 하나 늘고, 도메인 네임서버를 Cloudflare로 옮겨야 한다.
교내망에서 cloudflared의 아웃바운드가 막힐 가능성은 사전 테스트로 확인한다.

### 인증은 Auth.js v5, 로그인 수단은 DataGSM + Google 둘만

**상황**
초기에는 DataGSM 하나만 쓸 계획이어서 OAuth를 직접 구현하려 했다.
이후 Google과 이메일 로그인을 추가하기로 하면서 전제가 바뀌었다.

**선택지**
1. OAuth 직접 구현
2. Auth.js v5
3. Auth.js + 이메일/비밀번호 로그인 추가

**선택**
2번. 프로바이더는 DataGSM(커스텀) + Google 둘만.

**이유**
프로바이더가 늘면 계정 연결·세션·CSRF·state 검증 비용이 제곱으로 늘어난다.
이메일/비밀번호를 뺀 이유는 따로 있다 — 이메일 인증이 없는 비밀번호 가입을 허용하면,
공격자가 피해자 이메일로 먼저 가입한 뒤 피해자가 Google로 로그인할 때 계정이
연결되어 탈취된다(pre-hijacking). 그리고 비밀번호를 받는 순간 재설정·변경·
brute-force 방어까지 딸려온다. 학교 구성원은 Google과 DataGSM을 모두 갖고 있어
얻는 것이 거의 없다.

**대가**
학교 밖 사용자가 못 들어온다. 필요해지면 비밀번호 없는 매직 링크로 추가한다.

**주의**
Auth.js는 같은 이메일의 다른 프로바이더 계정을 기본적으로 자동 연결하지 않고
`OAuthAccountNotLinked` 에러를 던진다. DataGSM과 Google 모두 검증된 이메일을
주므로 이메일 기준 연결을 명시적으로 허용한다.

### 반복 할 일(루틴)은 조회 시점에 생성한다 (lazy materialization)

**상황**
"매주 월수금 러닝" 같은 루틴을 날짜별 체크 상태로 만들어야 한다.

**선택지**
1. cron으로 매일 새벽 미리 생성
2. 조회할 때 계산만 하고 저장 안 함
3. 해당 날짜를 조회하는 순간, 없으면 생성

**선택**
3번. `@@unique([routineId, date])` + `createMany({ skipDuplicates: true })`.

**이유**
1번은 cron이 한 번 실패하면 그날 아침 모두의 할 일이 비어 있고, 사용자가 가장 크게
체감하는 장애가 된다. 2번은 체크 상태를 저장할 행이 없어 애초에 불가능하다.
3번은 cron 없이 어느 환경에서도 동일하게 동작하고, 아무도 안 본 날짜는 데이터가
쌓이지 않으며, 루틴 내용을 수정해도 이미 생성된 과거 기록이 바뀌지 않는다.
동시 요청으로 인한 중복은 DB unique 제약이 막는다.

**대가**
생성 범위에 경계 조건이 두 개 필요하다.
- 미래 날짜: 생성하지 않고 화면에만 "예정"으로 표시. 체크할 때만 실제 생성.
  (안 그러면 캘린더를 몇 번 넘기는 것만으로 수천 행이 생긴다)
- 과거 날짜: 생성 하한을 `max(routine.startDate, user.createdAt, today - 30일)`로 제한.
  (안 그러면 과거로 스크롤할 때 미완료 루틴이 우수수 생겨 통계가 망가진다)

### E2E 테스트용 인증 우회 모드를 1일차에 넣는다

**상황**
Playwright가 Google이나 DataGSM 로그인 화면을 통과할 방법이 없다.
인증이 필요한 모든 테스트가 막히면 자동 반복 루프 전체가 무용지물이 된다.

**선택**
`AUTH_MODE=mock`일 때만 활성화되는 테스트 전용 Credentials 프로바이더를 둔다.
프로덕션 빌드에서 이 값이 켜져 있으면 빌드가 실패하도록 가드를 넣는다.

**이유**
나중에 붙이면 인증 코드를 전부 뜯어야 한다. Vercel Preview 배포는 URL이 매번
바뀌어 OAuth redirect URI 등록이 불가능하므로, 프리뷰에서도 이 모드가 필요하다.

**대가**
인증 경로가 둘이 된다. 가드가 뚫리면 심각하므로 빌드 타임 검증과
E2E 테스트로 이중 확인한다.

### 학교 데이터는 DataGSM 대신 NEIS를 직접 호출한다

**상황**
급식·시간표·학사일정을 DataGSM에서 받을 수 있다. 그런데 DataGSM 자체가
NEIS 데이터를 다시 서빙하는 중간 계층이다.

**선택**
급식·학사일정은 NEIS Open API 직접 호출. 시간표는 검증 후 결정.

**이유**
중간 계층을 빼면 장애 지점이 하나 줄고, 다른 학교로 확장할 수 있다.
인증은 여전히 DataGSM을 쓴다 — 재학생 확인은 NEIS로 대체할 수 없다.

**대가 / 미확인**
`hisTimetable`은 계열·학과·강의실 단위로 제공되는데, 마이스터고는 학과별 실습
블록이 많아 NEIS에 시간표가 비어 있는 경우가 흔하다. 실제 호출로 확인 전까지
시간표 기능은 착수하지 않는다. 비어 있으면 시간표만 DataGSM으로 폴백한다.
