# 설계 결정 기록

각 항목은 갈림길이 있었던 지점이다. 몇 달 뒤에 "이걸 왜 이렇게 짰지"에
답할 수 있도록 남긴다.

---

### 프로덕션은 Vercel, GSMSV는 백업·모니터링 노드로 시작

**상황**
교내 IaaS인 GSMSV를 쓰고 싶었다. 그런데 일반 사용자 VM은 `http://ssh.gsmsv.site:<포트>`로
평문 HTTP 접속만 제공한다. Google OAuth는 redirect URI에 `http://`를 localhost에서만
허용하므로 Google 로그인이 등록 단계에서 막힌다. PWA의 Service Worker도 secure context를
요구하고, 세션 쿠키에 `Secure` 플래그를 붙일 수 없어 교내망에서 세션 탈취가 가능하다.
추가로 일반 사용자 VM은 생성 30일 뒤 자동 삭제되며 복구가 불가능하다.

**선택지**
1. GSMSV에 바로 배포
2. Public IP 신청 후 GSMSV 배포 — 전체 7개 한정, 관리자 배정
3. Vercel로 시작하고 나중에 이관

**선택**
3번. 프로덕션은 Vercel + Neon, GSMSV는 2주차부터 백업·모니터링 노드로 사용.
PROJECT_OWNER 승인 후 이관을 별도 과제로 진행.

**이유**
1주차 목표가 "실제 URL에서 로그인이 된다"인데, 여기에 VM 세팅·Docker·Postgres·터널·
배포 파이프라인을 얹으면 일정이 3배가 된다. 그리고 VM을 만드는 순간 30일 시계가
돌기 시작해서, 세팅에 2주를 쓰면 절반을 태우게 된다.

**대가**
서버 운영 경험이 뒤로 밀린다. 이를 보완하기 위해 백업 노드(pg_dump + systemd timer +
SSH 키 + 방화벽)를 2주차에 먼저 붙인다. 서비스가 죽지 않으면서 같은 경험을 얻는다.

### HTTPS는 Cloudflare Tunnel로 해결 (이관 시점)

**상황**
GSMSV는 NAT 뒤에 있고 Public IP는 한정 자원이다. 도메인을 직접 연결하려면
Public IP가 필요하다고 안내되어 있다.

**선택지**
1. Public IP 신청 대기
2. Let's Encrypt를 VM에 직접 설치 — DNS를 제어하지 않아 HTTP-01 챌린지 불가
3. Cloudflare Tunnel

**선택**
3번.

**이유**
`cloudflared`가 아웃바운드로 Cloudflare에 연결하므로 인바운드 포트도 Public IP도
필요 없다. Cloudflare가 도메인의 HTTPS를 종단하므로 인증서 갱신도 자동이다.
앱은 `localhost:3000`에만 떠 있으면 되어 공격 표면이 오히려 줄어든다.

**대가**
Cloudflare에 의존이 하나 늘고, 도메인 네임서버를 Cloudflare로 옮겨야 한다.
교내망에서 cloudflared의 아웃바운드가 막힐 가능성은 사전 테스트로 확인한다.

### 인증은 Auth.js v5, 로그인 수단은 DataGSM + Google 둘만

**상황**
초기에는 DataGSM 하나만 쓸 계획이어서 OAuth를 직접 구현하려 했다.
이후 Google과 이메일 로그인을 추가하기로 하면서 전제가 바뀌었다.

**선택지**
1. OAuth 직접 구현
2. Auth.js v5
3. Auth.js + 이메일/비밀번호 로그인 추가

**선택**
2번. 프로바이더는 DataGSM(커스텀) + Google 둘만.

**이유**
프로바이더가 늘면 계정 연결·세션·CSRF·state 검증 비용이 제곱으로 늘어난다.
이메일/비밀번호를 뺀 이유는 따로 있다 — 이메일 인증이 없는 비밀번호 가입을 허용하면,
공격자가 피해자 이메일로 먼저 가입한 뒤 피해자가 Google로 로그인할 때 계정이
연결되어 탈취된다(pre-hijacking). 그리고 비밀번호를 받는 순간 재설정·변경·
brute-force 방어까지 딸려온다. 학교 구성원은 Google과 DataGSM을 모두 갖고 있어
얻는 것이 거의 없다.

**대가**
학교 밖 사용자가 못 들어온다. 필요해지면 비밀번호 없는 매직 링크로 추가한다.

**주의**
Auth.js는 같은 이메일의 다른 프로바이더 계정을 기본적으로 자동 연결하지 않고
`OAuthAccountNotLinked` 에러를 던진다. DataGSM과 Google 모두 검증된 이메일을
주므로 이메일 기준 연결을 명시적으로 허용한다.

### 반복 할 일(루틴)은 조회 시점에 생성한다 (lazy materialization)

**상황**
"매주 월수금 러닝" 같은 루틴을 날짜별 체크 상태로 만들어야 한다.

**선택지**
1. cron으로 매일 새벽 미리 생성
2. 조회할 때 계산만 하고 저장 안 함
3. 해당 날짜를 조회하는 순간, 없으면 생성

**선택**
3번. `@@unique([routineId, date])` + `createMany({ skipDuplicates: true })`.

**이유**
1번은 cron이 한 번 실패하면 그날 아침 모두의 할 일이 비어 있고, 사용자가 가장 크게
체감하는 장애가 된다. 2번은 체크 상태를 저장할 행이 없어 애초에 불가능하다.
3번은 cron 없이 어느 환경에서도 동일하게 동작하고, 아무도 안 본 날짜는 데이터가
쌓이지 않으며, 루틴 내용을 수정해도 이미 생성된 과거 기록이 바뀌지 않는다.
동시 요청으로 인한 중복은 DB unique 제약이 막는다.

**대가**
생성 범위에 경계 조건이 두 개 필요하다.
- 미래 날짜: 생성하지 않고 화면에만 "예정"으로 표시. 체크할 때만 실제 생성.
  (안 그러면 캘린더를 몇 번 넘기는 것만으로 수천 행이 생긴다)
- 과거 날짜: 생성 하한을 `max(routine.startDate, user.createdAt, today - 30일)`로 제한.
  (안 그러면 과거로 스크롤할 때 미완료 루틴이 우수수 생겨 통계가 망가진다)

### E2E 테스트용 인증 우회 모드를 1일차에 넣는다

**상황**
Playwright가 Google이나 DataGSM 로그인 화면을 통과할 방법이 없다.
인증이 필요한 모든 테스트가 막히면 자동 반복 루프 전체가 무용지물이 된다.

**선택**
`AUTH_MODE=mock`일 때만 활성화되는 테스트 전용 Credentials 프로바이더를 둔다.
프로덕션 빌드에서 이 값이 켜져 있으면 빌드가 실패하도록 가드를 넣는다.

**이유**
나중에 붙이면 인증 코드를 전부 뜯어야 한다. Vercel Preview 배포는 URL이 매번
바뀌어 OAuth redirect URI 등록이 불가능하므로, 프리뷰에서도 이 모드가 필요하다.

**대가**
인증 경로가 둘이 된다. 가드가 뚫리면 심각하므로 빌드 타임 검증과
E2E 테스트로 이중 확인한다.

### 학교 데이터는 DataGSM 대신 NEIS를 직접 호출한다

**상황**
급식·시간표·학사일정을 DataGSM에서 받을 수 있다. 그런데 DataGSM 자체가
NEIS 데이터를 다시 서빙하는 중간 계층이다.

**선택**
급식·학사일정은 NEIS Open API 직접 호출. 시간표는 검증 후 결정.

**이유**
중간 계층을 빼면 장애 지점이 하나 줄고, 다른 학교로 확장할 수 있다.
인증은 여전히 DataGSM을 쓴다 — 재학생 확인은 NEIS로 대체할 수 없다.

**대가 / 미확인**
`hisTimetable`은 계열·학과·강의실 단위로 제공되는데, 마이스터고는 학과별 실습
블록이 많아 NEIS에 시간표가 비어 있는 경우가 흔하다. 실제 호출로 확인 전까지
시간표 기능은 착수하지 않는다. 비어 있으면 시간표만 DataGSM으로 폴백한다.

### Prisma는 6.x로 고정한다 (7.x·8 RC 대신)

**상황**
버전을 지정하지 않고 설치했더니 npm의 `latest` 태그가 가리키던 `prisma@8.0.0-rc.15`가
깔렸고, `@prisma/client`는 7.10.0이라 CLI와 메이저 버전이 어긋났다. 8 RC CLI는 명령
체계가 달라서 Vercel 배포의 `postinstall`(`prisma generate`)이 `CLI.UNKNOWN_COMMAND`로
실패했다.

**선택지**
1. 8 RC 유지
2. 7.x 안정 버전으로 통일
3. 6.x 최신 안정 버전으로 통일

**선택**
3번. CLI와 client를 둘 다 `6.19.3`으로 정확히 고정했다(`^` 범위 없음).

**이유**
RC는 실서비스 DB 마이그레이션에 쓸 수 없다. 7.x는 드라이버 어댑터와 `prisma.config.ts`
설정이 추가로 필요하다. 6.x는 이미 작성된 스키마(`prisma-client-js`, datasource 안의
`url`/`directUrl`)를 그대로 쓸 수 있다. 정확한 버전으로 고정한 것은 CLI와 client가
다시 어긋나지 않게 하기 위해서다.

**대가**
7.x 이후 기능은 쓰지 못한다. 나중에 올릴 때는 datasource 수정, `prisma.config.ts` 추가,
어댑터 의존성 추가를 한꺼번에 하는 별도 작업이 되고, CLI와 client를 같은 버전으로
함께 올려야 한다. `package-lock.json`은 반드시 같이 커밋한다. Vercel은 `npm ci`로
lock 파일을 그대로 설치하므로, lock이 안 바뀌면 배포에서 8 RC가 다시 깔린다.

### 우회 로그인은 환경변수와 호스트 두 겹으로 막는다

**상황**
`AUTH_MODE=mock` 가드를 `VERCEL_ENV === "production"`으로만 걸어두었다. 그런데
로드맵에는 GSMSV 이관이 있고, 그곳은 Vercel이 아니라 `VERCEL_ENV`가 아예 없다.
즉 거기서는 우회 모드가 켜져 있어도 조용히 통과한다. 이메일만 아는 사람이 남의
계정으로 들어올 수 있다는 뜻이다.

**선택지**
1. `NODE_ENV=production`이면 무조건 막기
2. 배포 환경을 가리키는 자체 환경변수를 하나 더 두기
3. 요청 호스트로 한 번 더 막기

**선택**
3번. 모듈 로드 시점 가드(Vercel Production 빌드 실패)는 그대로 두고,
`authorize`에서 요청 호스트가 localhost이거나 Vercel Preview일 때만 통과시킨다.

**이유**
1번은 E2E가 프로덕션 빌드를 띄워 테스트하므로 그대로 막혀버린다. 2번은 환경변수를
하나 더 만드는 것이라, 그 변수를 빠뜨리면 똑같은 구멍이 다시 생긴다. 호스트는
배포 형태와 무관하게 요청마다 들어오는 값이라, 설정을 빠뜨려서 뚫리지 않는다.

**대가**
Preview 배포에서는 여전히 우회 로그인이 가능하다. 프리뷰 URL을 아는 사람만
접근할 수 있고, OAuth redirect URI를 등록할 수 없는 프리뷰에서 테스트하려면
필요한 통로다.

### 세션 전략을 평소와 테스트에서 다르게 쓴다

**상황**
세션은 DB에 저장하기로 했는데(Session 테이블), Auth.js의 Credentials 프로바이더는
DB 세션 전략을 지원하지 않는다. E2E 우회 로그인이 Credentials다.

**선택**
평소에는 `database`, `AUTH_MODE=mock`일 때만 `jwt`.

**이유**
DB 세션은 서버에서 세션을 즉시 무효화할 수 있다. 계정을 지우면 로그인도 끊긴다.
이 성질을 평상시에 포기할 이유가 없다. 우회 모드는 로컬과 프리뷰에서만 도는
테스트 통로이므로 JWT여도 잃는 것이 없다.

**대가**
인증 경로가 둘이므로 세션에서 사용자 id를 꺼내는 지점이 두 갈래다
(`user.id` / `token.sub`). 이 분기는 `lib/auth.ts`의 session 콜백 한 곳에만 둔다.

### 다크 모드는 CSS 변수와 data-theme으로 처리한다

**상황**
기기 설정을 따르면서도 사용자가 직접 고를 수 있어야 한다.

**선택**
색 값은 `--light-*` / `--dark-*`로 한 번만 정의하고, 배정만 세 곳에서 바꾼다.
기본(라이트) / `prefers-color-scheme: dark`이고 사용자가 라이트를 고르지 않은 경우 /
`[data-theme="dark"]`. 선택값은 localStorage에 넣고, 첫 페인트 전에 `<head>`의
동기 스크립트가 `data-theme`을 붙인다.

**이유**
클래스 토글 방식과 달리 컴포넌트가 `dark:` 변형을 알 필요가 없다. 화면 코드는
`bg-surface`, `text-muted` 같은 의미 이름만 쓴다. 동기 스크립트를 쓰는 이유는
React가 붙기 전에 색을 정해야 라이트로 한 번 번쩍이지 않기 때문이다.

**대가**
`<head>`에 인라인 스크립트가 하나 생긴다. 선택값은 기기별로 따로 저장되므로
다른 기기에서는 다시 골라야 한다. 계정에 저장하려면 User 컬럼이 필요하다.

### 닉네임은 DB와 앱 두 곳에서 막는다

**상황**
닉네임은 친구를 찾는 이름이라 겹치면 검색 결과에서 누가 누군지 알 수 없다.

**선택**
`User.nickname`에 unique 인덱스를 걸고, 저장 전에 앱에서 대소문자를 무시한 조회를
한 번 더 한다. 동시에 들어온 요청은 DB가 P2002로 막고, 그 경우 "방금 누군가 같은
닉네임을 가져갔어요."로 알린다.

**이유**
PostgreSQL의 unique 인덱스는 대소문자를 구분해서 `Modori`와 `modori`가 둘 다
들어간다. 사람 눈에는 같은 이름이므로 앱에서 한 겹 더 막아야 한다. 반대로 앱 검사만
두면 같은 순간에 들어온 두 요청이 둘 다 통과한다. 두 겹이 각자 다른 구멍을 막는다.

**대가**
저장할 때마다 조회가 한 번 늘어난다. `citext`나 함수 기반 인덱스를 쓰면 한 곳에서
끝나지만, 확장 설치나 Prisma가 다루지 못하는 인덱스가 필요해 미뤘다.

### 순서 바꾸기는 드래그와 화살표를 같이 둔다

**상황**
화살표만으로는 다섯 번째를 맨 위로 올리는 데 네 번을 눌러야 한다.

**선택**
dnd-kit으로 드래그를 붙이되, 기존 ↑↓ 버튼은 남긴다. 드래그 손잡이(`⠿`)를 따로 두고,
8px 넘게 끌어야 드래그로 본다. 저장 중에는 목록에 `aria-busy`를 붙인다.

**이유**
목록 전체를 잡게 하면 체크박스나 수정 버튼을 누를 수 없다. 손잡이를 분리하면 둘 다
된다. 화살표를 남기는 이유는 드래그가 키보드와 스크린리더에서 어렵기 때문이다.
`aria-busy`는 저장이 끝났는지 밖에서 알 수 있게 해준다. 드래그 직후 새로고침하면
저장 요청이 끊기는데, 이걸 테스트가 기다릴 방법이 달리 없었다.

**대가**
의존성이 세 개(`@dnd-kit/core`, `sortable`, `utilities`) 늘었다. 순서를 바꿀 때
그 날짜의 할 일을 전부 다시 쓴다. 하루치는 많아야 수십 개라 문제 없다.

---

### PWA는 manifest까지만 하고 Service Worker는 미룬다

**상황**
학교에서 쓰는 서비스라 주소를 매번 치는 것과 홈 화면 아이콘을 누르는 것은
실제 사용 빈도가 다르다.

**선택**
`app/manifest.ts`와 아이콘, 테마 색까지만 넣는다. Service Worker는 넣지 않는다.
아이콘은 `scripts/make-icons.mjs`가 코드로 굽는다.

**이유**
설치와 전체 화면은 manifest만으로 된다. Service Worker는 한 번 설치되면 사용자
기기에 남아서, 캐시 무효화를 잘못 짜면 고쳐서 배포해도 옛날 화면을 계속 본다.
되돌리려면 "이전 것을 지우는 Service Worker"를 또 배포해야 한다. 할 일 목록은
실시간 데이터라 어설프게 캐시하면 "분명히 체크했는데 안 되어 있다"가 된다.

**대가**
오프라인에서는 아무것도 안 열린다. 아이콘은 초록 바탕에 흰 체크뿐이라, 제대로 된
로고가 생기면 PNG로 바꿔 넣어야 한다.
