# 설계 결정 기록

각 항목은 갈림길이 있었던 지점이다. 몇 달 뒤에 "이걸 왜 이렇게 짰지"에
답할 수 있도록 남긴다.

항목마다 **상황 / 선택지 / 선택 / 이유 / 대가**를 적는다. 선택지에는 고르지 않은 길을, 대가에는 그 선택으로
포기한 것을 적는다. 2026-09-28 이전 항목 가운데 선택지가 빠져 있던 것은 그 항목의 상황·이유에 적힌
대안으로 채웠다(새로 지어내지 않았다).

### 프로덕션은 Vercel, GSMSV는 백업·모니터링 노드로 시작 — 바뀜(아래 "운영을 GSMSV로 옮긴다")

**상황**
교내 IaaS인 GSMSV를 쓰고 싶었다. 그런데 일반 사용자 VM은 `http://ssh.gsmsv.site:<포트>`로
평문 HTTP 접속만 제공한다. Google OAuth는 redirect URI에 `http://`를 localhost에서만
허용하므로 Google 로그인이 등록 단계에서 막힌다. PWA의 Service Worker도 secure context를
요구하고, 세션 쿠키에 `Secure` 플래그를 붙일 수 없어 교내망에서 세션 탈취가 가능하다.
추가로 일반 사용자 VM은 생성 30일 뒤 자동 삭제되며 복구가 불가능하다.

**선택지**
1. GSMSV에 바로 배포
2. Public IP 신청 후 GSMSV 배포 — 전체 7개 한정, 관리자 배정
3. Vercel로 시작하고 나중에 이관

**선택**
3번. 프로덕션은 Vercel + Neon, GSMSV는 2주차부터 백업·모니터링 노드로 사용.
PROJECT_OWNER 승인 후 이관을 별도 과제로 진행.

**이유**
1주차 목표가 "실제 URL에서 로그인이 된다"인데, 여기에 VM 세팅·Docker·Postgres·터널·
배포 파이프라인을 얹으면 일정이 3배가 된다. 그리고 VM을 만드는 순간 30일 시계가
돌기 시작해서, 세팅에 2주를 쓰면 절반을 태우게 된다.

**대가**
서버 운영 경험이 뒤로 밀린다. 이를 보완하기 위해 백업 노드(pg_dump + systemd timer +
SSH 키 + 방화벽)를 2주차에 먼저 붙인다. 서비스가 죽지 않으면서 같은 경험을 얻는다.

### HTTPS는 Cloudflare Tunnel로 해결 (이관 시점)

**상황**
GSMSV는 NAT 뒤에 있고 Public IP는 한정 자원이다. 도메인을 직접 연결하려면
Public IP가 필요하다고 안내되어 있다.

**선택지**
1. Public IP 신청 대기
2. Let's Encrypt를 VM에 직접 설치 — DNS를 제어하지 않아 HTTP-01 챌린지 불가
3. Cloudflare Tunnel

**선택**
3번.

**이유**
`cloudflared`가 아웃바운드로 Cloudflare에 연결하므로 인바운드 포트도 Public IP도
필요 없다. Cloudflare가 도메인의 HTTPS를 종단하므로 인증서 갱신도 자동이다.
앱은 `localhost:3000`에만 떠 있으면 되어 공격 표면이 오히려 줄어든다.

**대가**
Cloudflare에 의존이 하나 늘고, 도메인 네임서버를 Cloudflare로 옮겨야 한다.
교내망에서 cloudflared의 아웃바운드가 막힐 가능성은 사전 테스트로 확인한다.

### 인증은 Auth.js v5, 로그인 수단은 DataGSM + Google 둘만

**상황**
초기에는 DataGSM 하나만 쓸 계획이어서 OAuth를 직접 구현하려 했다.
이후 Google과 이메일 로그인을 추가하기로 하면서 전제가 바뀌었다.

**선택지**
1. OAuth 직접 구현
2. Auth.js v5
3. Auth.js + 이메일/비밀번호 로그인 추가

**선택**
2번. 프로바이더는 DataGSM(커스텀) + Google 둘만.

**이유**
프로바이더가 늘면 계정 연결·세션·CSRF·state 검증 비용이 제곱으로 늘어난다.
이메일/비밀번호를 뺀 이유는 따로 있다 — 이메일 인증이 없는 비밀번호 가입을 허용하면,
공격자가 피해자 이메일로 먼저 가입한 뒤 피해자가 Google로 로그인할 때 계정이
연결되어 탈취된다(pre-hijacking). 그리고 비밀번호를 받는 순간 재설정·변경·
brute-force 방어까지 딸려온다. 학교 구성원은 Google과 DataGSM을 모두 갖고 있어
얻는 것이 거의 없다.

**대가**
학교 밖 사용자가 못 들어온다. 필요해지면 비밀번호 없는 매직 링크로 추가한다.

**주의**
Auth.js는 같은 이메일의 다른 프로바이더 계정을 기본적으로 자동 연결하지 않고
`OAuthAccountNotLinked` 에러를 던진다. DataGSM과 Google 모두 검증된 이메일을
주므로 이메일 기준 연결을 명시적으로 허용한다.

### 반복 할 일(루틴)은 조회 시점에 생성한다 (lazy materialization)

**상황**
"매주 월수금 러닝" 같은 루틴을 날짜별 체크 상태로 만들어야 한다.

**선택지**
1. cron으로 매일 새벽 미리 생성
2. 조회할 때 계산만 하고 저장 안 함
3. 해당 날짜를 조회하는 순간, 없으면 생성

**선택**
3번. `@@unique([routineId, date])` + `createMany({ skipDuplicates: true })`.

**이유**
1번은 cron이 한 번 실패하면 그날 아침 모두의 할 일이 비어 있고, 사용자가 가장 크게
체감하는 장애가 된다. 2번은 체크 상태를 저장할 행이 없어 애초에 불가능하다.
3번은 cron 없이 어느 환경에서도 동일하게 동작하고, 아무도 안 본 날짜는 데이터가
쌓이지 않으며, 루틴 내용을 수정해도 이미 생성된 과거 기록이 바뀌지 않는다.
동시 요청으로 인한 중복은 DB unique 제약이 막는다.

**대가**
생성 범위에 경계 조건이 두 개 필요하다.
- 미래 날짜: 생성하지 않고 화면에만 "예정"으로 표시. 체크할 때만 실제 생성.
  (안 그러면 캘린더를 몇 번 넘기는 것만으로 수천 행이 생긴다)
- 과거 날짜: 생성 하한을 `max(routine.startDate, user.createdAt, today - 30일)`로 제한.
  (안 그러면 과거로 스크롤할 때 미완료 루틴이 우수수 생겨 통계가 망가진다)

### E2E 테스트용 인증 우회 모드를 1일차에 넣는다

**상황**
Playwright가 Google이나 DataGSM 로그인 화면을 통과할 방법이 없다.
인증이 필요한 모든 테스트가 막히면 자동 반복 루프 전체가 무용지물이 된다.

**선택지**
1. 테스트가 실제 Google·DataGSM 로그인 화면을 통과 — 방법이 없다
2. 우회 없이 시작하고 나중에 붙인다
3. 1일차에 테스트 전용 로그인을 넣는다

**선택**
`AUTH_MODE=mock`일 때만 활성화되는 테스트 전용 Credentials 프로바이더를 둔다.
프로덕션 빌드에서 이 값이 켜져 있으면 빌드가 실패하도록 가드를 넣는다.

**이유**
나중에 붙이면 인증 코드를 전부 뜯어야 한다. Vercel Preview 배포는 URL이 매번
바뀌어 OAuth redirect URI 등록이 불가능하므로, 프리뷰에서도 이 모드가 필요하다.

**대가**
인증 경로가 둘이 된다. 가드가 뚫리면 심각하므로 빌드 타임 검증과
E2E 테스트로 이중 확인한다.

### 학교 데이터는 DataGSM 대신 NEIS를 직접 호출한다

**상황**
급식·시간표·학사일정을 DataGSM에서 받을 수 있다. 그런데 DataGSM 자체가
NEIS 데이터를 다시 서빙하는 중간 계층이다.

**선택지**
1. DataGSM에서 받는다
2. NEIS Open API를 직접 부른다

**선택**
급식·학사일정은 NEIS Open API 직접 호출. 시간표는 검증 후 결정.

**이유**
중간 계층을 빼면 장애 지점이 하나 줄고, 다른 학교로 확장할 수 있다.
인증은 여전히 DataGSM을 쓴다 — 재학생 확인은 NEIS로 대체할 수 없다.

**대가 / 미확인**
`hisTimetable`은 계열·학과·강의실 단위로 제공되는데, 마이스터고는 학과별 실습
블록이 많아 NEIS에 시간표가 비어 있는 경우가 흔하다. 실제 호출로 확인 전까지
시간표 기능은 착수하지 않는다. 비어 있으면 시간표만 DataGSM으로 폴백한다.

### Prisma는 6.x로 고정한다 (7.x·8 RC 대신)

**상황**
버전을 지정하지 않고 설치했더니 npm의 `latest` 태그가 가리키던 `prisma@8.0.0-rc.15`가
깔렸고, `@prisma/client`는 7.10.0이라 CLI와 메이저 버전이 어긋났다. 8 RC CLI는 명령
체계가 달라서 Vercel 배포의 `postinstall`(`prisma generate`)이 `CLI.UNKNOWN_COMMAND`로
실패했다.

**선택지**
1. 8 RC 유지
2. 7.x 안정 버전으로 통일
3. 6.x 최신 안정 버전으로 통일

**선택**
3번. CLI와 client를 둘 다 `6.19.3`으로 정확히 고정했다(`^` 범위 없음).

**이유**
RC는 실서비스 DB 마이그레이션에 쓸 수 없다. 7.x는 드라이버 어댑터와 `prisma.config.ts`
설정이 추가로 필요하다. 6.x는 이미 작성된 스키마(`prisma-client-js`, datasource 안의
`url`/`directUrl`)를 그대로 쓸 수 있다. 정확한 버전으로 고정한 것은 CLI와 client가
다시 어긋나지 않게 하기 위해서다.

**대가**
7.x 이후 기능은 쓰지 못한다. 나중에 올릴 때는 datasource 수정, `prisma.config.ts` 추가,
어댑터 의존성 추가를 한꺼번에 하는 별도 작업이 되고, CLI와 client를 같은 버전으로
함께 올려야 한다. `package-lock.json`은 반드시 같이 커밋한다. Vercel은 `npm ci`로
lock 파일을 그대로 설치하므로, lock이 안 바뀌면 배포에서 8 RC가 다시 깔린다.

### 우회 로그인은 환경변수와 호스트 두 겹으로 막는다

**상황**
`AUTH_MODE=mock` 가드를 `VERCEL_ENV === "production"`으로만 걸어두었다. 그런데
로드맵에는 GSMSV 이관이 있고, 그곳은 Vercel이 아니라 `VERCEL_ENV`가 아예 없다.
즉 거기서는 우회 모드가 켜져 있어도 조용히 통과한다. 이메일만 아는 사람이 남의
계정으로 들어올 수 있다는 뜻이다.

**선택지**
1. `NODE_ENV=production`이면 무조건 막기
2. 배포 환경을 가리키는 자체 환경변수를 하나 더 두기
3. 요청 호스트로 한 번 더 막기

**선택**
3번. 모듈 로드 시점 가드(Vercel Production 빌드 실패)는 그대로 두고,
`authorize`에서 요청 호스트가 localhost이거나 Vercel Preview일 때만 통과시킨다.

**이유**
1번은 E2E가 프로덕션 빌드를 띄워 테스트하므로 그대로 막혀버린다. 2번은 환경변수를
하나 더 만드는 것이라, 그 변수를 빠뜨리면 똑같은 구멍이 다시 생긴다. 호스트는
배포 형태와 무관하게 요청마다 들어오는 값이라, 설정을 빠뜨려서 뚫리지 않는다.

**대가**
Preview 배포에서는 여전히 우회 로그인이 가능하다. 프리뷰 URL을 아는 사람만
접근할 수 있고, OAuth redirect URI를 등록할 수 없는 프리뷰에서 테스트하려면
필요한 통로다.

### 세션 전략을 평소와 테스트에서 다르게 쓴다

**상황**
세션은 DB에 저장하기로 했는데(Session 테이블), Auth.js의 Credentials 프로바이더는
DB 세션 전략을 지원하지 않는다. E2E 우회 로그인이 Credentials다.

**선택지**
1. 모두 JWT
2. 모두 DB 세션 — Credentials(우회 로그인)가 지원하지 않아 불가
3. 평소 DB 세션, 우회 모드만 JWT

**선택**
평소에는 `database`, `AUTH_MODE=mock`일 때만 `jwt`.

**이유**
DB 세션은 서버에서 세션을 즉시 무효화할 수 있다. 계정을 지우면 로그인도 끊긴다.
이 성질을 평상시에 포기할 이유가 없다. 우회 모드는 로컬과 프리뷰에서만 도는
테스트 통로이므로 JWT여도 잃는 것이 없다.

**대가**
인증 경로가 둘이므로 세션에서 사용자 id를 꺼내는 지점이 두 갈래다
(`user.id` / `token.sub`). 이 분기는 `lib/auth.ts`의 session 콜백 한 곳에만 둔다.

### 다크 모드는 CSS 변수와 data-theme으로 처리한다 — 선택지는 바뀜(아래 "테마는 라이트와 다크 둘만 고른다")

**상황**
기기 설정을 따르면서도 사용자가 직접 고를 수 있어야 한다.

**선택지**
1. 클래스 토글(컴포넌트마다 `dark:` 변형)
2. 색을 CSS 변수로 두고 `data-theme`으로 배정만 바꾼다

**선택**
색 값은 `--light-*` / `--dark-*`로 한 번만 정의하고, 배정만 세 곳에서 바꾼다.
기본(라이트) / `prefers-color-scheme: dark`이고 사용자가 라이트를 고르지 않은 경우 /
`[data-theme="dark"]`. 선택값은 localStorage에 넣고, 첫 페인트 전에 `<head>`의
동기 스크립트가 `data-theme`을 붙인다.

**이유**
클래스 토글 방식과 달리 컴포넌트가 `dark:` 변형을 알 필요가 없다. 화면 코드는
`bg-surface`, `text-muted` 같은 의미 이름만 쓴다. 동기 스크립트를 쓰는 이유는
React가 붙기 전에 색을 정해야 라이트로 한 번 번쩍이지 않기 때문이다.

**대가**
`<head>`에 인라인 스크립트가 하나 생긴다. 선택값은 기기별로 따로 저장되므로
다른 기기에서는 다시 골라야 한다. 계정에 저장하려면 User 컬럼이 필요하다.

### 닉네임은 DB와 앱 두 곳에서 막는다

**상황**
닉네임은 친구를 찾는 이름이라 겹치면 검색 결과에서 누가 누군지 알 수 없다.

**선택지**
1. DB unique 인덱스만 — 대소문자가 다른 같은 이름이 들어간다
2. 앱 검사만 — 동시에 온 두 요청이 둘 다 통과한다
3. `citext`나 함수 기반 인덱스 — 확장 설치나 Prisma가 못 다루는 인덱스가 필요하다
4. DB unique + 앱의 대소문자 무시 검사

**선택**
`User.nickname`에 unique 인덱스를 걸고, 저장 전에 앱에서 대소문자를 무시한 조회를
한 번 더 한다. 동시에 들어온 요청은 DB가 P2002로 막고, 그 경우 "방금 누군가 같은
닉네임을 가져갔어요."로 알린다.

**이유**
PostgreSQL의 unique 인덱스는 대소문자를 구분해서 `Modori`와 `modori`가 둘 다
들어간다. 사람 눈에는 같은 이름이므로 앱에서 한 겹 더 막아야 한다. 반대로 앱 검사만
두면 같은 순간에 들어온 두 요청이 둘 다 통과한다. 두 겹이 각자 다른 구멍을 막는다.

**대가**
저장할 때마다 조회가 한 번 늘어난다. `citext`나 함수 기반 인덱스를 쓰면 한 곳에서
끝나지만, 확장 설치나 Prisma가 다루지 못하는 인덱스가 필요해 미뤘다.

### 순서 바꾸기는 드래그와 화살표를 같이 둔다 — 바뀜(아래 "할 일 순서는 손잡이로만 바꾼다")

**상황**
화살표만으로는 다섯 번째를 맨 위로 올리는 데 네 번을 눌러야 한다.

**선택지**
1. 화살표만 둔다(기존)
2. 목록 줄 전체를 잡아 끈다
3. 손잡이로 끌고 화살표도 남긴다

**선택**
dnd-kit으로 드래그를 붙이되, 기존 ↑↓ 버튼은 남긴다. 드래그 손잡이(`⠿`)를 따로 두고,
8px 넘게 끌어야 드래그로 본다. 저장 중에는 목록에 `aria-busy`를 붙인다.

**이유**
목록 전체를 잡게 하면 체크박스나 수정 버튼을 누를 수 없다. 손잡이를 분리하면 둘 다
된다. 화살표를 남기는 이유는 드래그가 키보드와 스크린리더에서 어렵기 때문이다.
`aria-busy`는 저장이 끝났는지 밖에서 알 수 있게 해준다. 드래그 직후 새로고침하면
저장 요청이 끊기는데, 이걸 테스트가 기다릴 방법이 달리 없었다.

**대가**
의존성이 세 개(`@dnd-kit/core`, `sortable`, `utilities`) 늘었다. 순서를 바꿀 때
그 날짜의 할 일을 전부 다시 쓴다. 하루치는 많아야 수십 개라 문제 없다.

### PWA는 manifest까지만 하고 Service Worker는 미룬다

**상황**
학교에서 쓰는 서비스라 주소를 매번 치는 것과 홈 화면 아이콘을 누르는 것은
실제 사용 빈도가 다르다.

**선택지**
1. PWA를 하지 않는다
2. manifest만(설치·전체 화면)
3. manifest + Service Worker(오프라인 캐시)

**선택**
`app/manifest.ts`와 아이콘, 테마 색까지만 넣는다. Service Worker는 넣지 않는다.
아이콘은 `scripts/make-icons.mjs`가 코드로 굽는다.

**이유**
설치와 전체 화면은 manifest만으로 된다. Service Worker는 한 번 설치되면 사용자
기기에 남아서, 캐시 무효화를 잘못 짜면 고쳐서 배포해도 옛날 화면을 계속 본다.
되돌리려면 "이전 것을 지우는 Service Worker"를 또 배포해야 한다. 할 일 목록은
실시간 데이터라 어설프게 캐시하면 "분명히 체크했는데 안 되어 있다"가 된다.

**대가**
오프라인에서는 아무것도 안 열린다. 아이콘은 초록 바탕에 흰 체크뿐이라, 제대로 된
로고가 생기면 PNG로 바꿔 넣어야 한다.

### 날짜 격자의 링크는 미리 받지 않는다

**상황**
달력 한 칸마다, 주간 스트립 한 칸마다 `<Link href="/?date=...">`가 걸린다.
Next는 화면에 보이는 Link를 전부 미리 받는다.

**선택지**
1. Next 기본대로 보이는 링크를 모두 미리 받는다
2. 모든 링크에서 미리 받기를 끈다
3. 날짜 격자 안의 링크만 끈다

**선택**
날짜 격자 안의 링크에만 `prefetch={false}`를 준다. 하단 탭처럼 실제로 자주
누르는 링크는 그대로 둔다.

**이유**
달력을 한 번 열면 서버가 할 일 화면을 서른 번 그리고 있었다. 주간 스트립은
일곱 번이다. 그 화면은 질의를 대여섯 번 하므로, 커넥션 풀이 말라서 P2024로
페이지가 통째로 실패하는 일까지 생겼다. 날짜 칸은 누를 확률이 낮은 링크가
많은 쪽이라 미리 받는 이득보다 비용이 크다.

**대가**
날짜를 눌렀을 때 화면이 뜨는 시간이 조금 길어진다.

### 계정은 본인이 직접 지울 수 있어야 한다

**상황**
구글 계정으로 받은 이메일과 이름, 그리고 할 일 기록을 들고 있는데 그만두는
방법이 없었다.

**선택지**
1. 확인창 한 번으로 지운다
2. 지워질 것을 보여주고 닉네임을 직접 적어야 지운다
(지우는 순서: 계정 먼저 / 세션 먼저)

**선택**
설정 맨 아래에 작게 "계정 지우기"를 두고, 무엇이 몇 개 사라지는지 보여준 뒤
지금 닉네임을 그대로 입력해야 진행된다. 세션을 먼저 끊고 사용자 행을 지운다.

**이유**
확인창만으로는 실수로 지나간다. 닉네임을 직접 적게 하면 손이 멈춘다.
세션을 먼저 끊는 이유는, 계정을 먼저 지우면 Auth.js가 이미 사라진 세션 행을
지우려다 실패하기 때문이다. 이 순서에서는 중간에 실패해도 계정이 남으므로
다시 시도하면 된다.

**대가**
되돌릴 수 없다. 사용자 행 하나에 모든 관계가 Cascade로 달려 있어서,
할 일·카테고리·루틴·팔로우·반응이 함께 사라진다.

### 할 일 순서는 손잡이로만 바꾼다

**상황**
드래그를 넣으면서 화살표 버튼을 남겨뒀는데, 사용자가 쓰지 않는 버튼이라며
없애자고 했다. 원래 화살표를 남긴 이유는 키보드와 화면 읽기 프로그램이었다.

**선택지**
1. 화살표 버튼을 남긴다(키보드·화면 읽기 프로그램용)
2. 화살표를 없애고 손잡이의 키보드 조작과 우리말 안내로 대신한다

**선택**
할 일의 ↑↓ 버튼을 없앤다. 손잡이에서 스페이스로 집고 방향키로 옮기는 dnd-kit의
키보드 조작을 그대로 쓰고, 기본 영어 안내를 우리말로 바꾼다("둘을 3번째에
내려놓았어요"). 카테고리는 드래그가 없으므로 화살표를 그대로 둔다.

**이유**
키보드로 옮기는 길은 손잡이에 이미 있었다. 빠진 것은 무슨 일이 일어나는지
알려주는 안내였고, 그것을 채우면 화살표 없이도 같은 일을 할 수 있다.
키보드 이동은 E2E로 고정해서 나중에 끊기지 않게 한다.

**대가**
키보드 사용자는 스페이스-방향키-스페이스라는 조작법을 알아야 한다.
손잡이에 포커스가 가면 안내 문구로 알려준다.

### 지우기는 확인하지 않고, 되돌리기를 준다

**상황**
할 일과 루틴을 지울 때 브라우저 기본 확인창을 띄웠다. 사이트와 어울리지 않고,
매번 한 번 더 눌러야 했다.

**선택지**
1. 지울 때마다 확인창을 띄운다(기존)
2. 바로 지우고 몇 초 동안 되돌리기를 준다

**선택**
누르면 바로 지우고, 화면 아래에 "지웠어요 · 되돌리기" 알림을 5초 띄운다.
서버는 지운 내용을 돌려주고, 되돌리기는 그 값으로 같은 id의 행을 다시 만든다.
루틴은 연결돼 있던 할 일 id와 건너뛴 날까지 함께 돌려받아 다시 이어 붙인다.
계정 지우기만은 닉네임을 적는 확인을 남긴다.

**이유**
확인창은 습관적으로 넘기게 되어 실수를 잘 못 막는다. 지운 뒤 되살릴 수 있는 편이
빠르고 안전하다. 되돌리는 값은 브라우저에서 오므로, 카테고리와 루틴은 본인 것일
때만 다시 붙이고 할 일은 본인 것 중 비어 있는 것만 잇는다.
계정은 되돌릴 방법이 없어서 확인을 남긴다.

**대가**
할 일에 달려 있던 반응은 지울 때 함께 사라져 되돌려도 돌아오지 않는다.
알림이 사라진 뒤에는 되돌릴 수 없다.

---

### 루틴 할 일을 지운 날은 따로 남긴다

**상황**
루틴 할 일은 그 날짜를 열 때 없으면 만든다. 그래서 오늘이나 지난 날의 루틴
할 일을 지우면 화면을 다시 그리는 순간 되살아났다. 지우기가 한 번에 되면서
바로 드러날 문제였다.

**선택지**
1. Todo에 숨김 표시를 둔다
2. "만들지 않을 날"을 따로 적는 `RoutineSkip` 표

**선택**
`RoutineSkip(routineId, date)` 테이블을 추가한다. 루틴 할 일을 지우면 그 날을
기록하고, 할 일을 만들 때 기록된 날은 건너뛴다. 되돌리면 기록을 지운다.
루틴을 지우면 기록도 함께 사라진다.

**이유**
Todo에 숨김 표시를 두는 방법도 있었지만, 그러면 할 일을 읽는 모든 곳(오늘, 달력,
피드, 친구 화면, 개수)에서 숨김을 걸러야 하고 하나만 빠져도 지운 것이 새어 나온다.
"만들지 않을 날"은 만드는 쪽 한 곳에서만 보면 된다.

**대가**
테이블이 하나 늘었다. 추가만 하는 마이그레이션이라 기존 데이터는 그대로다.

### 탭은 피드·소셜·설정 셋, 달력은 피드 화면 왼쪽에 둔다 — "설정"은 2026-09-27에 "마이페이지"로 이름이 바뀜

**상황**
탭이 오늘·캘린더·피드·설정 넷이었다. 달력에서 날짜를 누르면 오늘 탭으로
넘어가서, 한 달을 보면서 그 날의 할 일을 고치려면 탭을 계속 오갔다.
카테고리와 루틴은 설정 안에 있어서, 할 일을 적다가 손보려면 멀리 돌아갔다.

**선택지**
1. 오늘·캘린더·피드·설정 네 탭을 둔다(기존)
2. 투두메이트 웹처럼 세 탭, 달력을 할 일 화면 왼쪽에 합친다
(좁은 화면: 달력을 늘 편다 / 접어 두고 주소로 편다)

**선택**
사용자 요청으로 투두메이트 웹처럼 바꾼다. "오늘"은 "피드"로, 친구 기능인
"피드"는 "소셜"로 이름을 바꾸고 캘린더 탭을 없앤다. 피드 화면은 넓은 화면에서
왼쪽에 한 달 달력, 오른쪽에 고른 날의 목록을 둔다. 좁은 화면에서는 주간 줄이
기본이고 "달력"을 누르면(`?view=month`) 달력을 편다. 카테고리와 루틴은
`/categories`, `/routines`로 옮기고 피드 화면에서 들어간다.
예전 주소(`/calendar`, `/settings/categories`, `/settings/routines`)는 새 주소로 넘긴다.
주소 `/feed`는 그대로 두고 이름만 소셜로 바꿨다.

**이유**
달력과 목록이 한 화면에 있으면 날짜를 눌러 바로 그 날을 고칠 수 있다.
좁은 화면에서 달력을 늘 펴두면 목록이 화면 아래로 밀려나서 접어둔다.
펴고 접는 상태를 주소에 두면 자바스크립트 없이 서버가 그리고, 뒤로 가기도 된다.

**대가**
피드 화면은 넓은 화면에서만 폭이 넓어진다(다른 화면은 한 칸이라 그대로).
화면 하나가 달력 질의까지 맡아서 질의가 하나 늘었다.

### 테마는 라이트와 다크 둘만 고른다

**상황**
테마 선택이 기기 설정·라이트·다크 셋이었다. 사용자가 기기 설정을 없애자고 했다.

**선택지**
1. 기기 설정·라이트·다크 셋을 둔다(기존)
2. 라이트·다크 둘, 처음에는 라이트
3. 라이트·다크 둘, 처음에는 기기 설정대로

**선택**
고르는 칸은 라이트와 다크 둘만 둔다. 아직 고르지 않은 사람은 기기 설정대로
시작하고, 버튼도 지금 보이는 쪽이 켜져 있다. 한 번 고르면 그 값을 저장한다.

**이유**
처음 들어온 사람에게 라이트를 강요하면 다크 모드 기기에서 화면이 한 번
하얗게 번쩍인다. 시작값으로만 기기 설정을 쓰면 선택지는 둘이면서 번쩍임도 없다.

**대가**
한 번 고른 뒤에는 기기 설정을 바꿔도 따라가지 않는다.

### 할 일은 카테고리 칩의 +로 적는다 — 아래로 내렸던 공용 입력 폼은 2026-09-21에 없앴다

**상황**
투두메이트 웹을 게스트로 열어 보니, 위쪽 공용 입력 폼이 없고 카테고리 칩마다
+가 있어서 그 자리에서 적는다. 할 일이 없는 카테고리도 늘 보인다.

**선택지**
1. 위쪽 공용 입력 폼 하나(기존)
2. 카테고리 칩마다 +
3. 칩의 +와 공용 폼을 같이(공용 폼은 아래로)

**선택**
피드 화면은 활성 카테고리를 모두 칩으로 보여주고, +를 누르면 칩 바로 아래에
입력칸이 열린다. Enter로 넣으면 입력칸이 비워진 채 열려 있어 연달아 적을 수 있고,
Esc로 닫는다. 공용 입력 폼은 없애지 않고 목록 아래로 내린다.

**이유**
카테고리를 고르고 적는 두 동작이 하나로 줄어든다. 공용 폼은 카테고리 없이 빨리
적을 때 쓸모가 있고, 여러 테스트가 기대고 있어서 남겼다. 대신 눈에 덜 띄게 둔다.

**대가**
같은 일을 하는 입력이 두 군데 있다. 칩의 + 버튼 이름에 "추가"를 넣으면 공용 폼의
"추가" 버튼과 섞여서 "공부에 할 일 쓰기"로 지었다.

### 날짜마다 클로버 표시를 붙인다 — 바뀜(칸 채우기를 거쳐 아래 "날짜 표시는 고양이 머리를 채운다")

**상황**
투두메이트는 달력과 주간 줄의 날짜 위에 작은 클로버를 둔다. 숫자만 있으면
어느 날 무엇을 했는지 훑어볼 수 없다.

**선택지**
1. 날짜 숫자만 둔다(기존)
2. 날짜마다 그날 한 일의 색으로 칠한 표시를 둔다

**선택**
한 일이 없으면 회색, 완료한 일이 있으면 그 카테고리 색으로 잎을 칠하고,
그 날 할 일을 전부 끝냈으면 흰 체크를 얹는다. 넓은 화면의 달력은 클로버 아래에
완료한 일 이름 칩도 둔다. 좁은 화면은 칸이 좁아 클로버만 둔다.

**이유**
색으로 어떤 종류의 일을 했는지, 체크로 다 끝냈는지를 한 글자도 읽지 않고 알 수 있다.

**대가**
달력을 그리려면 완료한 일뿐 아니라 그 달의 할 일 전체를 가져와야 한다.

### 캐릭터 "도리"는 직접 그린다 — 모양과 반응 쓰임은 바뀜(아래 "도리 표정을 반응으로 다시 쓴다")

**상황**
서비스만의 캐릭터와 공감 이모티콘이 있었으면 한다는 요청이 있었다.
무료 이모티콘 묶음도 쓸 수 있지만, 대개 저작권 표기나 사용 조건이 붙는다.

**선택지**
1. 무료 이모티콘 묶음을 쓴다 — 대개 저작권 표기나 사용 조건이 붙는다
2. 직접 그린다

**선택**
네 잎 클로버 모양의 초록 캐릭터 "도리"를 SVG로 직접 그린다(`components/dori.tsx`).
날짜의 클로버 표시와 같은 모양이라 서비스 안에서 한 줄로 이어진다.
표정은 인사, 새싹, 좋아요, 불타요, 대단해, 축하, 시무룩, 갸웃 여덟 가지다.
반응은 저장값(👍🔥👏🎉)을 그대로 두고 화면에서만 도리 표정과 이름으로 바꿔 그린다.

**이유**
직접 그린 원본이라 외부 표기 의무가 없고, 색과 모양을 서비스에 맞춰 마음대로 고칠 수 있다.
저장값을 바꾸지 않으면 이미 남긴 반응도 옮기지 않고 새 그림으로 보인다.
SVG라 이미지 파일을 내려받지 않고, 테마와 크기에 상관없이 또렷하다.

**대가**
그림을 고치려면 코드를 고쳐야 한다. 24px처럼 작게 쓰면 얼굴이 잘 안 보인다.

### 일정과 할 일을 나눈다 — 할 일 칸 채우기는 바뀜(아래 "날짜 표시는 고양이 머리를 채운다")

**상황**
시험 기간이나 발표처럼 "체크하는 것이 아니라 그 날 있는 일"을 할 일로 적으면,
끝내지도 못하고 목록만 어지럽힌다. 달력에 할 일 이름을 전부 적으면 칸이 넘친다.

**선택지**
1. 시험·발표 같은 일정도 할 일로 적는다(기존)
2. 일정 표를 따로 둔다
(달력: 할 일 이름을 모두 적는다 / 일정 이름만 적고 할 일은 채우기로)

**선택**
`Event` 테이블을 따로 둔다. 일정은 제목, 색, 시작일~종료일을 갖고 체크가 없다.
달력에는 일정 이름만 글자로 보이고, 할 일은 완료한 만큼 그 색으로 칸을 아래부터
채운다. 오른쪽 목록은 일정 칸이 위, 할 일이 아래다.

**이유**
둘은 다루는 방법이 다르다. 일정은 "언제"가 중요하고 할 일은 "했는지"가 중요하다.
달력에서 글자는 일정만 차지하게 두면, 할 일이 아무리 많아도 칸이 넘치지 않는다.
칸을 채우는 방식은 몇 개나 남았는지를 숫자 없이 보여준다.

**대가**
화면에 개념이 하나 늘었다. 일정은 친구에게 보이지 않는다(피드는 완료한 할 일만 흐른다).

### 보관한 카테고리의 루틴은 쉰다 — 예전 데이터에만 해당(아래 "카테고리는 보관 대신 삭제한다")

**상황**
카테고리를 보관하면 그 카테고리에 새 할 일을 적을 수 없다. 그런데 그 카테고리의 루틴은
매일 할 일을 계속 만들어서, 적을 수 없는 칸에 할 일만 쌓였다.

**선택지**
1. 루틴을 지운다
2. 루틴을 멈춤(pausedAt)으로 바꾼다
3. 데이터는 그대로 두고 조회 조건으로 쉬게 한다

**선택**
카테고리가 보관된 동안 그 루틴은 할 일을 만들지 않는다(`lib/routine-todos.ts`의 조회
조건). 루틴 자체는 지우거나 바꾸지 않고, 카테고리를 되살리면 다시 돈다.
루틴 화면에는 "카테고리 보관 중"으로 표시한다.

**이유**
보관은 "당분간 안 쓴다"는 뜻이다. 루틴을 지우면 되살릴 때 다시 만들어야 하고,
멈춤(pausedAt)으로 바꾸면 되살려도 멈춘 채라 사용자가 하나씩 다시 켜야 한다.
조회 조건으로 두면 데이터를 건드리지 않아 되돌리기가 자연스럽다.

**대가**
보관한 동안의 날짜는 되살린 뒤에도 채워지지 않는다(지난 날짜는 30일 안에서 그 날을
열 때 만들어지므로, 되살린 뒤 지난 날을 열면 그 날 것이 생길 수는 있다).

### 카테고리는 보관 대신 삭제한다 (2026-09-24, 사용자 결정)

**상황**

**선택지**
1. 보관을 그대로 둔다(기존)
2. 삭제하면서 그 안의 할 일도 지운다
3. 삭제하되 할 일은 "카테고리 없음"으로 남긴다(사용자 선택)

**선택**
- "삭제"는 카테고리만 지운다. 그 안의 할 일은 "카테고리 없음"으로 남는다(사용자 선택).
  지난 기록·받은 반응·통계는 그대로다.
- 그 카테고리의 루틴은 멈춘다. 카테고리 없이 계속 돌면 적을 수 없는 칸에 쌓인다.

- 순서 화살표는 없앴다. 순서는 만든 순서다.
- 예전에 보관한 카테고리는 보관함에 남고 되살릴 수 있다. 새로 보관하는 길은 없다.
- "카테고리 없음" 묶음에는 새로 적을 수 없다(카테고리 없이 적는 입력은 전에 없앴다).

**이유**
사용자가 보관보다 삭제를 원했다. 할 일까지 지우면 지난 기록·받은 반응·통계가 같이 사라지므로 할 일은 남긴다.

**대가**
"보관한 카테고리의 루틴은 쉰다" 결정은 예전 데이터에만 해당한다.
카테고리 순서를 바꿀 방법이 없었다 → 2026-09-28 카테고리 화면에서 손잡이로 끌어 바꾼다(할 일과 같은 `SortableList`).

### 요청 속도 제한은 앱 안에서 메모리로 센다 (2026-09-28)

**상황**
서버는 VM 한 대(2 vCPU)이고 초당 약 50화면에서 CPU가 찬다(`docs/capacity.md`). 한 사람이 스크립트로
요청을 몰아 보내면 모두가 느려진다. 서버 액션은 화면 밖에서도 부를 수 있다.

**선택지**
1. Cloudflare의 속도 제한 규칙 — 무료 플랜은 규칙 수와 조건이 좁고, 로그인한 사람을 구분하지 못한다
2. Redis 같은 저장소에 센다 — 서버가 하나라 저장소를 따로 둘 이유가 없다
3. 앱(`proxy.ts`) 안에서 토큰 버킷을 메모리에 둔다

**선택**
3번(`lib/rate-limit.ts`). 로그인한 사람은 세션마다 한 번에 60, 초당 6. 로그인 전은 접속 IP(`cf-connecting-ip`)마다
한 번에 300, 초당 30. 프로필 사진과 브라우저 오류 보고는 따로 센다. `/api/health`는 세지 않는다.

**이유**
학교 와이파이는 학생 전원이 공인 IP 하나로 나가서 IP로만 세면 한 반이 같이 막힌다. 로그인한 뒤에는 세션으로
나눠 센다. 앱은 Cloudflare Tunnel로만 들어오므로 `cf-connecting-ip`는 사용자가 꾸밀 수 없다.

**보완 (2026-09-28):** 임의의 `authjs.session-token` 쿠키만으로 세션 버킷을 주면 한 IP에서 쿠키를 바꿔
무한히 새 버킷을 만들 수 있었다. 선택지였던 요청마다 DB 조회는 부하가 크고, IP만으로 세는 것은 학교
와이파이에서 다른 학생을 함께 막는다. DB 세션은 발급할 때 `AUTH_SECRET`으로 서명한 무작위 토큰을 저장하고,
Proxy는 서명만 검증해 발급된 세션의 버킷을 구분한다. 테스트용 JWT 세션은 기존 Auth.js JWE를 검증한다.
검증되지 않은 쿠키(기존 DB 세션·서명 실패·만료 JWT)는 `cf-connecting-ip` 버킷으로 묶는다.
`x-forwarded-for`는 요청자가 앞에 값을 넣을 수 있으므로 신뢰하지 않는다. 서명 확인은 **로그인 권한 확인이 아니다**:
실제 세션 유효성·취소 여부는 기존 DB 인증이 계속 판단한다. 요청마다 DB를 조회하지 않는 대신 기존 세션은
다시 로그인하기 전까지 IP 제한을 공유한다. 데스크톱 코드 교환으로 새로 만드는 DB 세션에도 같은 서명을 쓴다.
비밀 키를 교체하면 기존 세션도 같은 제한을 공유한다.

**대가**
재시작하면 세던 값이 사라진다. 서버를 여러 대로 늘리면 저장소를 따로 둬야 한다.

### 오류 모니터링은 외부 서비스 없이 DB에 남긴다 (2026-09-28)

**상황**
운영에서 오류가 나도 알 방법이 없었다. Sentry 같은 서비스는 새 의존성과 외부 계정이 필요하다.

**선택지**
1. Sentry 같은 외부 서비스 — 새 의존성과 외부 계정
2. 우리 DB에 남기고 운영자 화면과 알림을 직접 만든다

**선택**

**이유**
의존성과 계정이 늘지 않고, 오류 내용이 우리 서버 밖으로 나가지 않는다. 저장소가 공개라 Actions 기록에는
내용을 남기지 않는다.

**대가**
코드 위치까지 추적하는 기능은 없다. 필요해지면 그때 Sentry로 옮긴다(의존성 추가라 사용자 승인 필요).

### 일정 시간은 날짜와 따로, 자정부터 몇 분으로 둔다 (2026-09-28, 사용자 요청)

**상황**
일정에 시간을 넣어 달라는 요청이 있었다. 날짜는 모두 `@db.Date`(시각 없음)에 한국 시간 기준으로 다룬다는 규칙이 있다.

**선택지**

2. 시각 열을 따로 더한다

**선택**
2번. `Event.startTime`·`endTime`(자정부터 분, 0~1439, 비면 하루 종일)을 더했다(열 추가만). 시작 시간은 시작일의,
끝 시간은 종료일의 시각이다. 폼과 화면은 "HH:MM"으로 주고받는다(`lib/event-time.ts`). 같은 날 일정은 하루 종일 → 시간순.

**이유**
날짜 규칙과 기존 데이터를 그대로 두고 시간만 얹는다. 시각을 분 단위 정수로 두면 정렬과 검사가 쉽다.

**대가**
시각에는 시간대가 없다. 모두 한국 시간이라고 본다.

### 데스크톱 앱은 웹을 띄우는 Electron으로, 로그인은 평소 브라우저에서 넘겨받는다 (2026-09-28, 사용자 결정)

2. Tauri
3. Electron(사용자 선택)

  페이지에 Node를 열지 않고(contextIsolation·sandbox), 모도리 밖 주소는 평소 브라우저로 연다.
- 앱 창에도 웹과 같은 로그인 버튼을 두고, 누르면 평소 브라우저에서 그 로그인을 이어 간다. 로그인을 마치면 서버가
  2분짜리 한 번 쓰는 코드를 `modori://`로 앱에 넘기고, 앱은 처음 만든 verifier와 함께 바꿔 세션을 받는다(PKCE).

PKCE를 쓰면 다른 프로그램이 `modori://` 링크를 가로채도 verifier가 없어 코드를 쓸 수 없다.

**대가**
설치 파일이 약 110MB다(Chromium을 같이 담는다). 코드 서명이 없어 SmartScreen 경고가 뜬다. 자동 업데이트가 없다.
더 가벼운 길(웹 앱 설치, Tauri)은 `docs/backlog.md` "앞으로 볼 것" 참고.

### 친구 화면에는 안 끝낸 일도 보인다 (2026-09-28, 사용자 요청)

**상황**
친구 화면(`/feed/u/[id]`)은 피드와 같이 팔로우한 사람의, 끝낸, 공개 카테고리 할 일만 보여줬다.
투두메이트처럼 친구가 오늘 무엇을 하려는지까지 보고 싶다는 요청이 있었다.

**선택지**
1. 끝낸 일만 보인다(기존)
2. 공개 카테고리의 할 일을 모두 보이고, 반응은 끝낸 일에만
3. 모두 보이고 안 끝낸 일에도 반응

**선택**
- 친구 화면은 공개 카테고리의 할 일을 끝냈든 아니든 다 보여준다. 안 끝낸 일은 내 화면과 같은 회색 네모, 끝낸 일은 묶음 아래로.
  묶음 옆 숫자는 "끝낸 수/전체", 달력과 주간 줄은 내 화면처럼 끝낸 만큼만 찬다.
- 반응은 여전히 끝낸 일에만 보낸다(`toggleReaction`의 `done: true` 그대로). 소셜 피드도 끝낸 일만 흐른다.
- 비공개 카테고리와 일정은 전과 같이 나만 본다.

**이유**
공개 카테고리는 "친구에게 보여줄 것"이라고 이미 골라 둔 것이다. 피드는 "끝냈다"는 소식이라 그대로 둔다.

**대가**
전에는 팔로워가 끝낸 일만 봤는데 이제 안 끝낸 일도 본다. 기존 사용자에게는 보이는 범위가 넓어진 것이라
개인정보처리방침 4번을 고쳤다.

### 지표는 외부 도구 없이, 쓴 날짜와 하루 합계로 센다 (2026-09-28, 사용자 요청)

**상황**
포트폴리오와 면접에 쓸 근거로 가입자·활성 사용자·재방문율 같은 숫자가 필요하다. 초기 숫자는 나중에 되살릴 수 없다.
지금 표로는 활성 사용자를 셀 수 없었다(마지막 접속 시각조차 없다).

**선택지**
1. 외부 분석 도구(Google Analytics, PostHog, Cloudflare Web Analytics)
2. 모든 요청·화면 이동을 사람별로 기록
3. 사람별로는 쓴 날짜만 90일 두고, 나머지는 매일 합계로 남긴다

**선택**
3번. `ActiveDay`(사람, 날짜)와 `DailyStat`(하루 합계)을 더했다(새 표만). `requireUser`가 하루 한 번 쓴 날을 적고,
그날 처음 적을 때 전날 합계를 찍는다. 이 기능 전의 쓴 날은 행동 기록으로 채웠다. 운영자만 `/admin/metrics`에서 본다.
화면별 이탈 대신 가입 단계(로그인 → 닉네임 → 할 일 → 팔로우 → 반응)로 본다. 정의는 `docs/metrics.md`.

**이유**
주간 활성과 재방문율은 "그날 썼는가"만 있으면 셀 수 있다. 1번은 추적 쿠키나 새 국외 이전 업체가 생기고 새 의존성이다.
2번은 개인정보가 훨씬 커지는데, 사용자가 수십 명이라 화면별 비율은 한두 명에 뒤집히는 잡음이다.
합계를 따로 찍는 것은 계정·할 일이 지워지고 쓴 날짜가 90일 뒤 지워져도 그날의 숫자를 남기기 위해서다.

**대가**
화면별 이탈, 쓰는 시간대, 머문 시간은 모른다. 늦게 채운 합계는 그사이 지워진 기록을 셀 수 없어 적게 나올 수 있다(처음에는 전날 것만 찍었다. 2026-09-29 외부 기여 PR #110·#111을 합쳐
빠진 날을 30일씩 뒤에서 채우고, 쓴 날짜 정리는 합계와 따로 오늘 포함 90일 기준으로 한다. 보관 약속이 복구보다 먼저다).
90일 지난 사람별 기록이 없어 옛 가입자를 새 기준으로 다시 셀 수 없다. 운영자 계정도 센다.

### 할 일·일정 메모는 본인만 본다 (2026-09-28, 사용자 요청)

**상황**
할 일이나 일정에 준비물·범위 같은 몇 줄을 덧붙이고 싶다는 요청이 있었다. 글자 밑에 메모가 보여야 한다.

**선택지**
1. 메모를 친구에게도 보인다(공개 카테고리 할 일과 함께)
2. 메모는 본인만 본다
(입력: 할 일 창의 Enter 저장을 그대로 / 저장 버튼을 더한다)

**선택**
2번. `Todo.memo`, `Event.memo`(열 추가만, 500자). 할 일 창과 일정 폼에 메모 칸을 두고, 목록에서는 글자 밑에 세 줄까지 보인다.
할 일 창에 "저장" 버튼을 더했다. 할 일 칸의 Enter는 예전처럼 저장하고, 메모 칸의 Enter는 줄바꿈이다. 지웠다 되돌리면 메모도 돌아온다.

**이유**
메모에는 할 일보다 사적인 내용(점수, 개인 사정)이 들어가기 쉽다. 친구 화면은 방금 안 끝낸 일까지 보이게 넓혔는데,
메모까지 보이면 공개 범위가 사용자 예상보다 커진다. 여러 줄을 적으려면 Enter가 줄바꿈이어야 해서 저장 버튼이 필요하다.

**대가**
친구에게 보여 주고 싶은 메모도 보여 줄 수 없다. 원하면 카테고리처럼 공개 여부를 고르게 해야 한다.

### "다른 날에 하기"는 날짜를 골라 옮기고, 루틴 할 일은 루틴에서 뗀다 (2026-09-28, 사용자 요청)

**상황**
할 일을 눌렀을 때 다른 날을 직접 골라 그날로 옮기고 싶다는 요청이 있었다. 루틴 할 일은 그 날짜를 열 때 없으면 만들어지고,
`(routineId, date)`가 unique다.

**선택지**
1. 날짜만 바꾼다 — 루틴 할 일이면 원래 날에 루틴이 다시 만들고, 옮긴 날에 같은 루틴 할 일이 있으면 막힌다
2. 루틴 할 일은 옮기지 못하게 한다
3. 루틴 할 일은 루틴에서 떼어 보통 할 일로 옮기고, 원래 날은 건너뛴다고 남긴다(`RoutineSkip`)
(날짜 고르기: "내일" 같은 정해 둔 버튼 / 날짜 칸)

**선택**
3번. 할 일 창의 "다른 날에 하기"를 누르면 날짜 칸(처음 값은 다음 날)이 열리고 "옮기기"로 옮긴다(`moveTodo`).
옮긴 날의 맨 아래에 붙고 완료 여부·색·메모·받은 반응은 그대로다. 오늘에서 1년 안, 옮긴 날도 하루 50개 상한을 지킨다.
같은 날로는 옮기지 않는다.

**이유**
"오늘 못 한 루틴을 내일로 미루기"가 가장 흔한 쓰임인데 2번은 그걸 막는다. 1번은 옮기자마자 원래 날에 같은 할 일이 되살아난다.
날짜 칸 하나면 내일·다음 주·지난날 모두 된다.

**대가**
옮긴 루틴 할 일은 더 이상 루틴 기록(루틴 화면의 완료 비율)에 들어가지 않는다. 매일 루틴을 내일로 옮기면 내일에는
옮긴 것과 내일의 루틴 할 일이 둘 다 있다. 되돌리기는 없다(다시 옮기면 된다).

### 운영 배포는 같은 커밋의 verify가 통과한 뒤에만 한다 (2026-09-29, 이슈 #112)

**상황**
`deploy.yml`은 `main`에 push되면 바로 배포했고, `verify.yml`은 따로 돌았다. 검증이 실패한 커밋도 운영에 올라갈 수 있었다.
평소에는 로컬에서 `npm run verify`를 돌린 뒤 합쳐서 드러나지 않았다.

**선택지**
1. 그대로 둔다(로컬 검증을 믿는다)
2. 한 워크플로 안에서 검증 작업 뒤에 배포 작업을 둔다(`needs`)
3. `workflow_run`으로 `verify`가 끝난 뒤 배포를 시작하고, `main` push에서 성공한 실행의 커밋만 받는다

**선택**
3번. `verify` 성공 + 이벤트가 `push`일 때만, 그 실행의 `head_sha`를 받아 배포한다. 손으로 돌리는 급한 배포(`workflow_dispatch`)는 남긴다.

**이유**
2번은 PR과 `main`에서 검증을 두 벌 관리하게 되고, `verify`의 DB 공유 줄 세우기(concurrency)와 배포 줄 세우기가 섞인다.
3번은 기존 두 워크플로를 그대로 두고 연결만 한다. 이벤트를 `push`로 좁혀서 PR(포크 PR 포함)의 검증은 배포로 이어지지 않는다.

**대가**
합친 뒤 운영에 뜨기까지 CI 검증 시간(약 8~10분)만큼 늦어진다. 테스트가 일시적으로 깨지면 배포도 멈춰서 검증을 다시 돌려야 한다.
급한 배포는 검증 없이 나가므로 사람이 확인해야 한다(`deploy/README.md`).

### 데스크톱 릴리스는 태그·버전이 맞고 두 플랫폼이 다 만들어진 뒤에만 올린다 (2026-09-29, 이슈 #114)

**상황**
`desktop.yml`은 태그를 올리면 Windows·macOS를 각각 만들고 각자 릴리스에 올렸다. 태그 번호와 `desktop/package.json`의 version을
비교하지 않았고, 한쪽이 실패하면 설치 파일이 하나뿐인 릴리스가 공개됐다.

**선택지**

2. 버전 확인만 더한다
3. 버전 확인 + 두 플랫폼을 만든 뒤 한 작업에서 릴리스를 만들고 올린다

**선택**

**이유**
마이페이지의 "Windows 앱 받기"는 가장 최근 릴리스를 가리켜서, 반쪽 릴리스가 생기면 한쪽 사용자는 바로 받을 파일이 없다.
버전이 다르면 앱이 스스로 알리는 버전과 릴리스 이름이 어긋난다.

**대가**
릴리스가 두 플랫폼 중 느린 쪽이 끝날 때까지 늦어진다. 출시 승인 절차는 따로 두지 않았다(태그를 올리는 사람이 운영자다).
이 변경은 다음 태그를 올릴 때 처음 돈다.

### 폰에서 느리다: 탭 화면을 30초 동안 다시 쓰고 하단 탭은 미리 받아 둔다 (2026-10-03, 사용자 요청)

**이유**

가입한 사람 누구든 무작위로 노출된다. 닉네임으로 검색하면 어차피 누구나 찾히지만, 이름을 몰라도 목록으로 훑게 된다. 방침 4항(시행일 10월 7일)에 적었다. 가입자가 수천 명이 되면 `ORDER BY md5`는 전체를 훑으므로 다시 봐야 한다(지금은 수십~수백 명이라 문제 없다).

### 추천 친구에서 빠지는 스위치와 운영자 사용자 화면 (2026-10-07, 사용자 요청)

**상황**
친구 추천을 넣자 (1) 추천에 나오고 싶지 않은 사람이 있고, 운영자가 특정 사용자를 추천에서 빼야 하며, (2) 공개 첫 주에 "누가 쓰고 누가 멈췄는지"를 사람 단위로 봐야 했다. 지금 지표 화면은 합계뿐이다.

**선택지**
1. 추천은 모두에게 나오게 둔다 / 마이페이지 스위치(`User.hideFromRecommend`)를 둔다
2. 특정 사용자를 빼는 방법: 닉네임을 코드·마이그레이션에 적는다 / 같은 스위치 값을 운영 DB에서 직접 켠다
3. 운영자 화면: 지표 화면에 사람별 표를 붙인다 / 따로 `/admin/users`를 만든다

**선택**
스위치를 두고(기본은 나옴), 특정 사용자는 운영 DB에서 그 스위치 값을 직접 켰다(공개 저장소에 사람 이름을 남기지 않으려고 코드·마이그레이션에는 적지 않는다). 운영자 화면은 `/admin/users`로 따로 만들었다: 사용자별 가입일·경로·로그인 방법·최근 사용·쓴 날·할 일(완료/전체)·카테고리·루틴·일정·팔로잉·팔로워·보낸/받은 반응·프로필·푸시·추천 여부, 정렬·검색, 요약 타일. 개수와 날짜만 보이고 내용은 읽지 않는다. CSV에는 닉네임·이메일·id가 없다.

**이유**
스위치는 사용자가 스스로 정하게 하고, 운영자의 예외는 같은 값을 쓰면 규칙이 하나다. 사람별 표는 지표(합계)와 다른 목적(개별 이탈 확인)이라 화면을 나눴다.

**대가**
추천을 끄는 일은 닉네임 검색을 막지 않는다(검색은 서비스의 기본 기능). 운영자가 특정 사용자를 빼면 그 사람의 스위치도 꺼진 것으로 보여 마이페이지에서 켜 둘 수 있다. 운영자 화면은 이메일을 보여 주므로 방침에 적었고, 사용자가 수천 명이 되면 한 번에 모두 세는 방식(최대 500명)을 다시 봐야 한다.


### 검색 엔진에는 /login·/privacy·/terms만 알리고 대표 주소를 지정한다 (2026-10-07, Search Console 메일)

**상황**
Search Console이 "리디렉션이 포함된 페이지"와 "사용자가 선택한 표준이 없는 중복 페이지" 때문에 색인이 안 된다고 알렸다. 앞의 것은 `http→https`, `www→modori.site`, 로그인 전 `/`·`/?from=…`가 `/login`으로 가는 리디렉션으로 정상이다. 뒤의 것은 `/login`에 `?next=…`·`?error=…`·`?switch=1`이 붙은 주소가 같은 내용인데 대표 주소가 없어서였다.

**선택지**
1. 그대로 둔다(로그인한 사람만 쓰는 서비스라 검색 노출이 필요 없다)
2. 로그인·방침·약관에 대표 주소(canonical)를 달고 사이트맵을 넣어, 서비스 이름 검색에 로그인 화면이 깨끗하게 나오게 한다
3. 로그인 화면도 색인하지 않는다(noindex)

**선택**
2번. 로그인 화면은 `?`가 붙어도 대표 주소를 `/login`으로 알리고, `app/sitemap.ts`가 `/login`·`/privacy`·`/terms`만 알린다. `robots`는 온보딩·앱 로그인 중계·운영자 화면을 막는다. 리디렉션 주소는 손대지 않는다(리디렉션은 그대로가 맞다).

**이유**
"모도리"를 검색한 사람이 처음 만나는 곳이 로그인 화면이다. 3번은 서비스 이름 검색에서 사이트가 안 나오게 한다.

**대가**
Search Console은 재크롤 뒤(며칠~몇 주)에야 "중복" 경고가 줄어든다. 리디렉션 경고는 구조상 남는다(오류가 아니라 정보).

### 첫 화면에 큰 "첫 할 일 적기" 버튼, 팔로우가 없는 소셜 화면에 추천 친구 (2026-10-07, 공개 첫날 데이터)

**상황**
공개 첫날 데이터(10/7): 가입 61명 중 할 일을 한 번이라도 쓴 사람은 14명(23%), 10/6~10/7 가입 40명 중 35명이 한 번도 안 썼다. 접속은 했다(오늘 49명). 61명 중 51명(84%)이 아무도 팔로우하지 않았고 반응을 보낸 사람은 4명이다. 새 계정으로 첫 화면을 찍어 보니 할 일을 쓰는 방법이 작은 "오늘" 칩과 작은 글씨 안내뿐이었다. 소셜 탭의 빈 화면에도 "닉네임으로 찾아보기" 링크뿐이었다.

**선택지**
1. 그대로 둔다(보고 나간 사람이 많고 첫날 숫자라 흔들린다)
2. 홈 빈 화면에 큰 버튼, 소셜 빈 화면에 추천 친구를 바로 보여 준다
3. 가입 직후 안내 투어를 띄운다(화면이 늘고 건너뛰는 사람이 많다)

**선택**
2번. 홈은 오늘·앞날이고 할 일이 하나도 없을 때만 "첫 할 일 적기" 버튼을 보인다(누르면 첫 카테고리의 입력칸이 열리고 포커스가 간다). 소셜은 팔로우가 0일 때만 추천 친구 세 명을 보인다(어제 만든 추천 부품을 그대로 쓰고 다시 뽑기는 그 화면에 머문다). 사람 줄과 추천 칸을 공용 부품(`person-row`, `recommended-friends`)으로 뺐다.

**이유**
첫날 사용자가 기능을 못 찾아서 나간 것과 서비스를 보러만 온 것을 데이터만으로는 가를 수 없지만, 입력칸이 어디인지 모르는 화면은 확실한 결함이다. 고치는 비용이 작고 기존 사용자 화면은 그대로다. 효과는 다음 수치로 본다: 신규 가입자 중 첫 할 일을 쓴 비율(10/7 기준 5/40), 팔로우한 비율.

**대가**
버튼은 입력칸을 직접 열지 않고 카테고리 칩을 눌러 주는 방식이라(입력칸의 상태가 칩에 있다) 칩의 접근성 이름("…에 할 일 쓰기")에 기댄다. 칩 문구를 바꾸면 이 버튼도 같이 고쳐야 한다(시험이 잡는다). 첫날 하루치라서 효과 판단은 1~2주 데이터로 한다.

### 사람마다 시간대를 골라 "오늘"을 정한다 (2026-10-08, 사용자 결정·요청: 캐나다에 있는 친구)

**상황**
모도리의 "오늘"은 모든 사용자가 Asia/Seoul 기준이었다(`lib/date.ts`, CLAUDE.md 규칙 2). 캐나다(서울보다 13~14시간 느림)에 사는 친구는 현지 저녁에 이미 서울이 다음 날이라 "오늘"이 내일로 넘어가 있고, 할 일 날짜·루틴·달력의 오늘 표시·기록이 어긋났다.

**선택지**
1. 서울 기준을 유지하고 안내만 한다
2. 사용자마다 시간대(`User.timezone`, IANA 이름)를 고르게 하고, 그 시간대에서 "오늘"을 센다. 날짜 값(`@db.Date`)은 시각 없는 달력의 날이라 그대로 두고, 운영자 지표는 서울 기준으로 둔다
3. 기기의 시간대를 자동으로 따라간다(여행·VPN·기기 설정에 따라 날이 흔들리고, 사용자가 의도하지 않은 변화가 생긴다)

**선택**
2번. 마이페이지의 "시간대"에서 나라·도시 34곳 중 하나를 고른다(기본 서울, 목록 밖의 값은 서버가 받지 않는다). 기기 시간대가 다르면 한 번에 맞추는 버튼을 보여 준다. 오늘·새 할 일의 날짜·할 일/일정 옮기기의 범위·루틴 생성·기록의 "오늘까지"·날짜 창·자정 넘김 감지가 모두 그 시간대를 쓴다. 클라이언트는 `TimezoneProvider`로 알린다. 서머타임과 30분·45분 시차는 오프셋을 직접 더하지 않고 `Intl`이 계산한다(`dateIn`). 새 의존성은 없다.

**이유**
날짜는 사람이 쓰는 "달력의 날" 표시라 다른 사람이 보는 화면에는 시차 계산이 필요 없다(서울 사람은 캐나다 친구가 쓴 "10월 7일" 할 일을 그대로 본다). 바뀌는 것은 "지금이 어느 날이냐"뿐이다. 3번은 사용자가 모르는 사이 날이 바뀌는 사고를 낸다.

**대가**
- 같은 순간 사람마다 "오늘"이 다르다. 친구의 "오늘 한 일"이 내 오늘과 다른 날일 수 있다(날짜 값이라 틀리지는 않는다).
- 운영자 지표(가입자, 쓴 날짜 `ActiveDay`, 하루 합계)와 `lib/daily.ts`는 서울 기준이다. 해외 사용자가 늘면 "그날 쓴 사람"이 서울 달력으로 세어진다는 점을 `docs/metrics.md`에서 알고 읽어야 한다.
- 시간대를 바꾸는 순간 "오늘"이 하루 이동할 수 있다. 이미 쓴 할 일의 날짜는 바뀌지 않는다.
- 소셜의 "완료한 시각" 같은 순간(instant)은 서울/보는 사람 기준이 섞여 있다(알림의 팔로우 날짜만 보는 사람 시간대로 맞췄다).
