# 지표

무엇을 세는지, 왜 세는지, 어떻게 모으는지. 숫자는 운영자만 `/admin/metrics`(마이페이지 맨 아래 "지표")에서 본다.
2026-09-28에 정했다. 초기 숫자는 나중에 되살릴 수 없어서 출시 첫날부터 쌓는다.

## 1. 세는 것

| 지표 | 정의 | 왜 보나 |
|---|---|---|
| 가입자 수 | 닉네임까지 정해 가입을 마친 계정(누적, 지운 계정은 빠진다) | 서비스가 퍼지고 있는지 |
| 주간 활성 사용자 | 그날까지 7일 동안 하루라도 쓴 사람 | 가입만 하고 떠난 사람과 실제로 쓰는 사람을 가른다. 할 일 앱의 진짜 크기는 이 숫자다 |
| 재방문율(7일) | 어느 날 가입한 사람 가운데 다음 날부터 7일 안에 하루라도 다시 쓴 비율 | 첫인상 뒤에 남는지. 이게 낮으면 가입자를 늘려도 밑 빠진 독이다 |
| 할 일 작성 수 | 그날 직접 적은 할 일(루틴이 만든 것은 뺀다) | 핵심 행동이 실제로 일어나는지. 루틴 할 일은 화면을 열기만 해도 생겨서 뺀다 |
| 친구 연결 수 | 팔로우 연결 수, 한 명 이상 팔로우한 사람 수 | 친구가 모도리와 다른 투두 앱의 차이다. 친구가 없는 사람에게 반응 기능은 없는 것과 같다 |
| 반응 수 | 그날 보낸 반응 | 연결이 실제로 오가는 응원이 되는지. 연결만 있고 반응이 없으면 소셜은 장식이다 |
| 이탈 지점 | 가입 단계별 남은 사람: 로그인 → 가입 완료(닉네임) → 할 일 적음 → 팔로우함 → 반응 보냄, 그리고 7일 재방문 | 어느 단계에서 가장 많이 멈추는지 알아야 무엇부터 고칠지 정한다 |

| 가입 경로 | 어느 링크로 와서 가입했는지(`User.signupSource`)와 경로별 누적(`DailyStat.sources`). 새 열이 생기기 전(9/28~10/3)에 찍힌 하루 합계는 `lib/metrics.ts`의 `backfillStatColumns`가 지금 남은 계정·반응으로 다시 세어 채웠다(지운 계정만큼 적을 수 있고, 그때는 모두 `direct`). 경로별로 가입 → 할 일 → 팔로우 → 반응 → 7일 안에 씀까지 | 사람을 모으는 길(디스코드·카카오톡·스토어·직접 입력) 가운데 어디가 남는 사람을 데려오는지. 출시 첫 주 숫자는 되살릴 수 없다 |
| 반응 종류 | 캐릭터 표정 반응 대 이모지(`DailyStat.reactionsCharacter`), 지금 화면에서는 캐릭터별·인기 이모지 | 새로 만든 캐릭터가 실제로 쓰이는지, 어느 캐릭터가 사랑받는지 |
| 프로필 선택 | 사진을 올린 사람 수, 캐릭터별 선택 수(지금 계정 기준) | 캐릭터 프로필이 쓰이는지 |

### 화면별 이탈은 세지 않는다

"어느 화면에서 나갔는가"는 세지 않고 위의 가입 단계로 대신한다.

- 화면별로 세려면 모든 화면 이동을 사람마다 기록해야 한다. 지금 모으는 것(쓴 날짜)보다 개인정보가 훨씬 커진다.
- 사용자가 수십 명이면 화면별 이탈률은 한두 명의 행동으로 뒤집히는 잡음이다.
- "할 일을 한 번도 안 적고 떠났다"처럼 행동 단위로 보는 편이 고칠 곳을 바로 가리킨다.

사용자가 수백 명을 넘어 화면 단위가 필요해지면 아래 4번의 외부 도구를 다시 검토한다.

### 넣지 않은 것

- 체류 시간, 페이지뷰: 할 일 앱은 짧게 열고 닫는 게 잘 쓰는 것이라 길다고 좋은 게 아니다.
- 완료율: 사람마다 적는 방식(크게 하나 / 잘게 여럿)이 달라 비교할 뜻이 없다. 통계 화면에서 본인만 본다.

## 2. 모으는 방법

외부 도구 없이 우리 DB에 둔다(`lib/metrics.ts`).

| 무엇 | 어디 | 언제 | 얼마나 |
|---|---|---|---|
| 쓴 날짜 | `ActiveDay`(사람, 날짜) | 가입을 마친 사람이 로그인한 채 화면을 열거나 무언가를 하면 하루 한 번(`requireUser`) | 오늘 포함 최근 90일(오늘~89일 전)만 남기고 하루 한 번 지운다. 실패하면 같은 날 다음 요청이 다시 한다. 계정을 지우면 같이 지운다 |
| 하루 합계 | `DailyStat`(날짜, 숫자들) | 로그인한 요청이나 `health` 감시 때 어제까지 빠진 날을 뒤에서 채운다(`lib/daily.ts`, 한 번에 최대 30일) | 계속. 사람과 잇지 않은 숫자라 개인정보가 아니다 |
| 가입 경로 | `User.signupSource` | 초대 링크의 `?from=` 값을 `lib/signup-source.ts`의 head 스크립트가 브라우저 localStorage(`modori-from`)에 처음 한 번 적고, 가입(온보딩)할 때 서버로 보낸다. 쿠키를 쓰지 않는다. 모양(소문자·숫자·하이픈 20자)이 틀리면 버리고 가입은 그대로 한다(`lib/signup-source.ts`). 앱 안에서 연 화면은 user agent 꼬리표(`ModoriMobile`)로 `app-android`, 로그인 링크에도 `from=app-android`를 실어 시스템 브라우저에서도 이어진다 | 계정이 있는 동안. 하루 합계에는 경로별 누적 숫자만 남는다 |
| 누적(가입 단계, 팔로우 수) | 원래 표(`User`·`Todo`·`Follow`·`Reaction`)를 센다 | 지표 화면을 열 때, 그리고 하루 합계에 | — |

- 하루 합계는 한국 자정 기준이다. 가입자·팔로우 같은 누적은 그날 끝까지 만든 것, 할 일·반응은 그날 만든 것이다.
- 하루 합계가 필요한 이유: 할 일·반응·계정은 나중에 지워지고, 쓴 날짜는 90일 뒤 지운다. 합계를 찍어 두지 않으면
  몇 달 뒤 "출시 첫 주에 몇 명이 썼나"에 답할 수 없다.
- 재방문율은 가입 7일 뒤에야 셀 수 있어서, 하루 합계의 `cohortSize`·`cohortReturned`는 **그날의 7일 전 가입자**를 센다.
- 알고 있는 빈틈
  - 서버가 며칠 꺼져 있었어도 다시 켜진 뒤 빠진 날을 채운다. 다만 늦게 찍은 합계는 그사이 지워진 계정·할 일을 셀 수 없어
    실제보다 적을 수 있고, 쓴 날짜 보관 기간(90일)보다 오래된 날은 채우지 않는다(2026-09-29, PR #110·#111을 합쳐 반영).
  - 이 기능 전(2026-09-28까지)의 쓴 날짜는 마이그레이션이 행동 기록(가입, 할 일 적기·완료, 일정·루틴, 반응, 팔로우)으로
    채웠다. 화면만 보고 간 날은 빠져 실제보다 적다.
  - 운영자 본인 계정도 센다. 사용자가 적을 때는 한 명이 크다.

### 내려받기

`/admin/metrics`의 "CSV 받기"(`/admin/metrics/export`, 운영자만)가 하루 합계 전체를 CSV로 준다. 엑셀·구글 시트에서 그래프를 그린다.
열: 날짜, 계정, 가입자, 단계별 사람 수, 하루·주간 활성, 할 일·반응·캐릭터 반응, 재방문 분모·분자, 경로별 누적(JSON).

### 출시 때 쓸 링크

공지에는 경로를 붙인 링크를 쓴다. 표시가 없으면 `direct`로 센다.

| 어디에 | 링크 |
|---|---|
| 디스코드 | `https://modori.site/?from=discord` |
| 카카오톡 | `https://modori.site/?from=kakao` |
| 인스타그램·SNS | `https://modori.site/?from=sns` (곳을 나누려면 `insta`처럼 이름을 바꾼다) |
| 학교 게시판·소개 글 | `https://modori.site/?from=school` |
| 모바일·데스크톱 앱 | 따로 붙이지 않는다. 앱에서 시작한 가입은 `app-android`(모바일), `app-desktop`(Windows 앱)으로 센다 |

경로 이름은 소문자·숫자·하이픈 20자까지다. 한 사람이 여러 링크를 거쳐도 **처음 닿은 링크**가 남는다.
로그인 전에 링크를 열면 서버가 `/login?next=...`로 보내서 `from`이 `next` 안으로 들어가는데, `lib/signup-source.ts`가 그것도 읽는다(테스트로 고정).
카카오톡 안에서 연 링크는 로그인이 막혀 "다른 브라우저로 열기"로 옮기는데, 그때 열리는 주소(`/login?next=...?from=kakao`)에도 `from`이 들어 있어 밖의 브라우저에서 다시 적힌다.

## 3. 해석할 때

- 비율은 늘 분모와 같이 본다. 지표 화면은 재방문율 옆에 `(다시 온 사람/가입한 사람)`을 같이 보여준다.
- 가입 단계는 "지금까지 한 번이라도"다. 예전 가입자일수록 다음 단계에 있을 시간이 많았다.
- 숫자가 바뀐 이유가 기능 때문인지 보려면 `docs/decisions.md`·`docs/handoff.md`의 날짜와 맞춰 본다.

## 4. 외부 도구를 붙인다면

지금은 붙이지 않았다. 붙이기 전에 사용자 승인(새 서비스·새 의존성)을 받고, 개인정보처리방침(`lib/privacy.ts`)과
`docs/privacy-inventory.md`를 같은 커밋에서 고친다.

| 도구 | 얻는 것 | 방침에 더할 것 |
|---|---|---|
| Cloudflare Web Analytics | 화면별 방문 수, 들어온 경로, 기기 종류 | 1번(자동 수집)에 "방문한 화면 주소·브라우저 종류 같은 접속 통계", 2번(쓰는 곳)에 "방문 통계". Cloudflare는 이미 5번에 있다. 쿠키를 쓰지 않는다고 안내하므로 7번은 그대로(붙일 때 Cloudflare 문서로 다시 확인) |
| Google Analytics, PostHog 같은 제품 분석 | 사람별 화면 흐름, 화면별 이탈 | 추적 쿠키(7번 "추적 쿠키 쓰지 않아요" 문장을 바꿔야 한다), 새 국외 이전 업체(5번), 수집 항목(기기 식별자, 화면 이동 기록). 권하지 않는다 |

### 정식 공개 직전 기준선 (2026-10-03 하루 합계)

공개 전에 이미 20명이 가입해 있다(테스트·지인). 그래서 공개의 효과는 총 가입자가 아니라 **10/6 이후 증가분**과 **그 사람들의 재방문**으로 본다.
`cohortSize`·`cohortReturned`는 가입한 날 기준이라 공개 뒤 가입자만 따로 본다.

## 시간대 (2026-10-08)

사용자는 마이페이지에서 시간대를 고를 수 있지만(`User.timezone`), **지표의 날짜 기준은 계속 Asia/Seoul**이다(`ActiveDay`, 하루 합계, 재방문). 해외 사용자의 "그날 쓴 사람"은 서울 달력으로 세어진다. 해외 사용자가 눈에 띄게 늘면 그때 기준을 다시 정한다.
