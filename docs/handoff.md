## 2026-09-21 — DataGSM 토큰 형식과 캐릭터 재설계

### DataGSM: 확인한 사실

추측 대신 실제로 측정했다. 비밀값은 출력하지 않았다.

- **authorize 요청에 state가 없었다.** 로컬에서 `/api/auth/signin/datagsm`의 302
  Location을 찍어 확인했다. `checks: ["pkce"]`라서 파라미터 자체가 생성되지 않는다.
  나머지(response_type, scope, redirect_uri, code_challenge, S256)는 문서와 일치했다.
  `checks: ["state", "pkce"]`로 되돌린 뒤 state와 `authjs.state` 쿠키가 생기는 것을 확인했다.
- **PKCE 쿠키는 정상이었다.** authorize 직후 `authjs.pkce.code_verifier`가 저장된다.
- **토큰 엔드포인트는 JSON 본문 + 본문 자격 증명만 받는다.** 일부러 틀린 code로
  세 형식을 보내 응답을 비교했다.
  - JSON 본문 + client_id/client_secret → 400 `invalid_grant` (형식·인증 통과)
  - JSON 본문 + Basic 헤더 → 401 "잘못된 형식의 Authorization 헤더입니다"
  - form 본문 → 415 "지원되지 않는 미디어 타입입니다"
  기존 코드는 customFetch가 Authorization 헤더를 지우는데 본문에도 자격 증명이 없어서
  어떤 인증도 실리지 않았다. `client_secret_post`로 바꿔 본문에 들어가게 했다.
- **scope는 `datagsm:self_read`가 맞다.** `SELF_READ`로 보내면 400 `invalid_scope`다.
- authorize 엔드포인트는 state가 없어도 302를 준다. 즉 로그인 화면까지는 간다.
  로그인 이후 콜백에서 무엇이 돌아오는지는 실제 계정이 있어야 확인된다.

### DataGSM: 해결됨 (2026-09-21 확인)

아래 "남은 확인"은 해결 전 절차이므로 참고용으로만 남긴다.

### DataGSM: (해결 전) 남은 확인

프로덕션에서 DataGSM 로그인을 한 번 더 시도한 뒤, Vercel 로그의 `[auth:error]` 한 줄이
필요하다. 이제 `providerError`와 `providerErrorDescription`을 함께 남긴다.
authorization code와 토큰은 로그에 남지 않는다.

- `providerError: invalid_request` 계열이면 DataGSM이 콜백에 오류를 실어 보낸 것이다.

- `message`에 `unexpected "iss"`가 있으면 DataGSM이 RFC 9207 `iss`를 보내는 것이므로
  provider에 `issuer`를 정확한 문자열로 지정해야 한다. 값은 DataGSM 쪽에 확인해야 한다.

## 2026-09-22 — 하단바 흔들림과 검증 속도

### 하단바

화면마다 하단 탭의 비율이 달라 보였다. 크기를 직접 재 보니 헤드리스에서는

그때마다 화면 폭이 그만큼 줄어 가운데 정렬된 하단 탭과 내용이 좌우로 밀린다.
`html { scrollbar-gutter: stable }`로 자리를 늘 비워 둔다.

### 검증 13.3분 → 3.1분

E2E를 `workers: 1`로 묶어 둔 이유는 계정 이름이 파일마다 고정이라 파일끼리
서로의 계정을 지웠기 때문이다. 이름에 실행 꼬리표를 붙여 그 문제를 없애고
파일끼리 병렬로 돌린다(로컬 4, CI 2). `fullyParallel: false`라 한 파일 안의
순서는 그대로 지켜진다.

### CI가 main에서만 실패하던 이유

`feed.spec.ts`의 팔로우 테스트가 CI에서 세 번 연달아 깨졌다. 로컬과 PR 검사는
통과했다. 원인은 코드가 아니라 **계정 이름이 실행마다 같다는 것**이었다.
`testInfo.testId`는 실행이 달라도 같은 값이라, 로컬 검증과 CI가 같은 Neon
데이터베이스에서 같은 계정을 만들고 지운다. CI가 팔로우를 누르는 사이 로컬이
그 계정을 지우면 `followUser`가 대상을 못 찾고 조용히 끝나, 버튼이 "팔로우 중"으로
바뀌지 않는다. `tests/e2e/run-tag.ts`의 꼬리표로 실행끼리 겹치지 않게 했다.

## 2026-09-23 — 기록(통계) 화면

투두메이트 앱스토어 설명과 우리 화면을 다시 비교했다. 타이머·일기·AI·위젯은
영구 제외 항목이라 빼면, 남는 공백은 **통계**였다. 우리는 "이번 달 완료 N개"가
전부라 어느 카테고리를 잘 지키는지도, 며칠째 이어왔는지도 알 수 없었다.

`/stats`를 만들었다. 달마다 끝낸 개수·해낸 비율·이어온 날, 카테고리별 막대,
요일별 막대를 보여준다.

- 세는 규칙은 `lib/stats.ts`에 순수 함수로 뒀다. DB도 화면도 필요 없어서
  단위 테스트로 경계를 잡는다(`tests/unit/stats.test.ts`).
- **이어온 날은 오늘이 비어 있으면 어제부터 센다.** 그러지 않으면 자정을 넘기는
  순간 쌓아온 날이 0으로 보인다.
- 이어온 날은 달 경계를 넘으므로 1년치를 따로 읽는다. 달 통계만 읽으면
  1일에 항상 0이나 1이 된다.

## 2026-09-23 — 속도 측정과 D-day

### 속도: 앱이 아니라 거리 문제다

정적 파일(`/icon.svg`)과 서버 컴포넌트(`/login`)의 TTFB를 나란히 쟀다.

정말 줄이려면 DB를 서울 리전으로 새로 만들고 함수도 icn1로 보내는 수밖에 없다.
이건 데이터 이전이라 베타 전에 따로 판단한다.

### D-day

투두메이트 앱스토어 리뷰에서 가장 많이 요청되는 기능이다. 우리도 같은 구멍이
있었다. 일정에 날짜가 있는데 그 날짜를 열어보기 전에는 며칠 남았는지 몰랐다.

- `lib/dday.ts` — 시작 전이면 `D-n`, 시작한 날이면 `D-DAY`, 여러 날짜리의
  가운데면 "진행 중", 끝난 일정이면 null. 순수 함수라 단위 테스트로 잡는다.

  숫자로 뒤덮인다.
- 오늘 화면에 아직 오지 않은 일정 세 개를 같이 띄운다. 그러지 않으면 D-day를
  만들어 놓고도 그 날짜로 옮겨가야만 보인다.

## 2026-09-23 — 반응 열둘과 도리 다듬기

- **눈에 반짝임을 넣었다.** 검은 타원만 있으면 인형 눈처럼 멍해 보인다.
  이게 인상을 가장 크게 바꿨다.
- 꼬리를 붙였다. 옆선이 밋밋하면 어느 쪽이 앞인지 덜 읽힌다.
- 배를 아주 옅게 밝혔다. 진하게 하면 몸이 흰 덩어리로 뭉쳐 발이 사라진다

## 2026-09-23 — 팔레트 여덟 색, 진행 막대 고정, 친구 화면 달력

### 팔레트

빨주노초파보 + 흰색 + 검정, 무지개 순서로 여덟 개만 둔다. 색이 많으면 무엇을
골랐는지 기억하지 못하고 비슷한 색끼리 구별도 안 된다.

**흰색과 검정이 들어오면서 색을 글씨에 쓰던 곳이 전부 깨진다.** 흰 글씨는
라이트 모드에서, 검정 글씨는 다크 모드에서 배경과 같아진다. 그래서
카테고리 칩은 색을 **배경으로** 쓰고 글씨는 `contrastTextColor`로 고른다.
색 견본과 색 점에는 얇은 테두리를 둘렀고, 완료 체크의 ✓도 대비로 고른다.

`DEFAULT_EVENT_COLOR`가 `PALETTE[1]`을 가리키고 있었다. 팔레트가 바뀌면 같이
바뀌므로 파랑을 직접 적었다. 새 가입자의 `Today's`도 파랑이다.

### 진행 막대

할 일이 없어도 `0개 중 0개 완료`로 자리를 지킨다. 첫 할 일을 적는 순간 막대가
생기면 화면이 한 번 밀리고, 무엇이 늘었는지도 알아채기 어렵다.
"할 일" 제목은 지웠다. 바로 아래가 할 일 목록이라 말할 필요가 없다.

### 문구

`{오늘|이 날} 할 일을 다 끝냈어요` → `할 일을 다 끝냈어요`.
친구 화면의 `이 날 끝낸 할 일이 없어요`도 `끝낸 할 일이 없어요`로 줄였다.
날짜는 바로 위에 이미 적혀 있다.

### 친구 화면

내 오늘 화면과 같은 구성으로 맞췄다. 넓은 화면에서는 왼쪽 프로필·달력,
오른쪽 목록. 좁은 화면에서는 주간 줄과 "달력" 버튼. 날짜 화살표도 넣었다.
`PageFrame`이 `/`만 넓게 쓰고 있어서 `/feed/u/`도 넓히도록 고쳤다.

### 도리

360px로 띄워 놓고 어디가 어색한지 찾았다.

- **꼬리를 뺐다.** 굵기를 줄이고 위치를 옮겨도 계속 앞발로 보였다.
- **어깨를 좁혔다.** 머리와 몸통이 같은 폭이라 목이 없고 한 덩어리로 보였다.
- 볼터치가 얼굴 절반을 덮고 있어 줄였다.
- 파티 고깔이 귀 바깥에 떠 있어 머리 위로 옮겼다.

## 2026-09-24 — 흰색 견본 테두리, 뒤로가기, 팔 달린 도리

### 흰색 견본이 라이트 모드에서 안 보였다

앞서 테두리를 넣었다고 했는데, 팔레트 견본이 아니라 "지금 쓰는 색" 견본에만
넣었다. 게다가 라이트 모드 테두리 색(`#e8ebed`)은 흰 배경에서 거의 안 보인다.

`globals.css`에 `.color-edge`를 만들었다. 글자색을 22% 섞은 안쪽 선이라
라이트에서는 어두운 선, 다크에서는 밝은 선이 알아서 생긴다. 색 견본, 색 점,
카테고리 칩, 완료 체크, 일정·루틴 색 점에 모두 쓴다.

### 뒤로가기

글자 `←` 하나라 누를 수 있는 면적이 글자 크기뿐이었고, 흐린 색이라 버튼으로
보이지도 않았다. `components/back-link.tsx`에 40px 동그라미 + 꺾쇠 아이콘을
만들고 아홉 화면을 모두 바꿨다. 왼쪽 여백만큼 당겨서 아이콘이 본문 선에 맞는다.

### 도리: 팔을 달고 2등신으로

머리가 몸의 대부분이라 1.5등신에 가까웠고 팔이 없었다.

- 머리를 0.84배로 줄여 위로 올렸다. 얼굴 좌표를 전부 다시 적는 대신 **머리 묶음째
  변환**한다(`HEAD`). 줄인 만큼 테두리가 가늘어지므로 머리에는 선을
  `OUTLINE / HEAD_SCALE`로 준다.
- 몸통을 넓고 둥글게, 발을 그 아래에. 머리 하나에 몸 하나, 두 등신 남짓이다.
- **팔은 몸 뒤에 그린다.** 어깨가 옆구리에 숨어 몸에서 뻗어 나온 것처럼 보인다.
  위에 얹으면 막대가 몸에 붙어 있는 것처럼 보인다.
- 파티 고깔은 머리를 따라가야 해서 얼굴(머리 좌표)로 옮겼다.

### 로그인 로고

104px에서 64px로 줄였다. 버튼 두 개 위에 로고만 크게 떠 있었다.

### 테스트

`profile.spec.ts`가 고정 닉네임(`처음닉네임`)을 쓰고 있었다. 이메일에는 실행
꼬리표가 붙어 매번 바뀌므로, 중간에 끊긴 실행이 남긴 옛 계정은 지워지지 않고
닉네임만 붙잡고 있다. 닉네임에도 꼬리표를 붙였다.

## 2026-09-24 밤 — 자율 개선 루프 (사용자 요청: 10회)

사용자가 자는 동안 찾기 → 고치기 → 검증 → 재확인 → 배포를 열 번 돈다.
루프마다 여기에 무엇을 찾았고 무엇을 고쳤는지 남긴다.

### 루프 1 — 서버 액션 보안·권한

여덟 개 액션 파일을 전부 읽었다. 남의 데이터를 건드리는 구멍은 없었다(모든
갱신이 `userId`로 걸러진다). 대신 아래를 찾아 고쳤다.

- **보관한 카테고리에 새 할 일이 들어갈 수 있었다.** 화면은 막지만 `addTodo`는
  `archivedAt`을 보지 않았다. 다른 탭에서 보관하기 전에 열어 둔 입력칸이 남아
  있으면 들어간다. `archivedAt: null`을 조건에 넣었다.
- **반응을 같은 순간 두 번 누르면 오류 화면이 떴다.** 둘 다 "없으니 만든다"로
  가서 unique 제약(P2002)에 걸린다. 그 오류는 결과가 같으므로 넘긴다.
- **잘못된 날짜 문자열 하나가 오류 화면을 띄웠다.** `parseKSTDate`는 예외를
  던지는데 `addTodo`·`restoreTodo`·`completeScheduledRoutine`·`reorderTodos`가
  그대로 불렀다. `readDay`로 감싸 null이면 조용히 돌아간다.
- **카테고리 창이 저장하지 않고도 "저장했어요"라고 했다.** 이름을 비운 채 색을
  바꾸면 서버는 조용히 돌아가는데 화면은 성공이라고 했다. `updateCategory`가
  결과를 돌려주고 화면은 "이름을 적어주세요"를 빨갛게 띄운다. E2E로 고정했다.
- **카테고리 색이 팔레트 밖 값도 받았다.** 정규식만 보고 아무 16진 색이나
  받았다. 만들 때는 팔레트만, 고칠 때는 팔레트이거나 원래 쓰던 색만 받는다.

검증: `npm run verify` 통과 — 단위 70×3, E2E 62/62(카테고리 창 테스트 2개 추가).

### 루프 2 — 모바일 라이트 전 화면

두 계정에 카테고리·할 일·일정·루틴·팔로우·반응을 채워 넣고 19개 화면을 찍어
한 장씩 봤다(점검 스크립트는 저장소에 넣지 않고 scratchpad에서 돌린다).

- **(회귀 버그) 고른 색에 선택 링이 안 보였다.** 흰색 테두리용 `.color-edge`가
  `box-shadow`를 썼는데 Tailwind `ring`도 `box-shadow`다. 레이어 밖 규칙이라 항상
  이겨서 링을 지웠다. `border`로 바꾸고 `@layer components` 안에 넣었다.
- **진한 색 위 글씨가 탁했다.** `contrastTextColor`는 대비가 큰 쪽을 고르는데,
  파랑(#3b82f6)은 검정 쪽이 조금 더 커서 파란 칩에 검정 글씨가 올라갔다.
  굵은 글씨·아이콘용 `onColorText`를 만들어 흰 글씨와 3:1 이상이면 흰색을 쓴다.
  빨강·파랑·보라·검정 → 흰 글씨, 주황·노랑·초록·흰색 → 어두운 글씨.
- **소셜 피드가 할 일마다 큰 카드였다.** 이름과 날짜가 줄마다 반복되고 네 개면

### 루프 7 — 성능: 조회와 페이로드

인덱스는 실제 조회 모양과 잘 맞았다(할 일 `userId+date`, 피드 `userId+done+doneAt`,
일정 `userId+startDate`). 반복문 안에서 DB를 부르는 곳도 없다.

**문제는 페이로드였다.** 프로필 사진이 data URL로 DB에 있고, 그걸 `<img src>`에 그대로
넣었다. 사진 한 장이 약 9KB인데 아바타를 그리는 곳마다 HTML에 실리고, Next가 같은 값을
화면 데이터(RSC)에 한 번 더 싣는다. 사진 있는 친구 한 명의 열흘치 피드만으로
**같은 사진이 20번, `/feed`가 236KB**였다. 게다가 피드 조회가 할 일마다 사진을 DB에서
끌어왔다(할 일 50개면 같은 사진 50번).

- `app/api/avatar/[id]/route.ts`가 사진을 이미지로 내려준다. 로그인한 사람만 받는다.
- 주소는 `lib/avatar.ts`의 `avatarUrl`이 만든다. 사진 내용에서 뽑은 짧은 값을 `?v=`로
  붙여서, 사진을 바꾸면 주소가 바뀐다. 그래서 1년 캐시를 걸어도 옛 사진이 남지 않는다.
  공용 CDN에는 두지 않는다(`private`).
- 피드는 할 일에서 사진을 빼고, 사람마다 한 번만 읽는다.

**재확인:** `/feed` 236KB → 52KB(−78%), 페이지 안 data URL 0개. 사진 주소는 로그인한
요청에 `200 image/jpeg`(원본과 같은 6,800바이트), 로그인 안 한 요청에 `401`.
`profile.spec.ts`가 "img src가 data URL과 같다"를 보고 있어서, 주소로 내려오고 브라우저가
실제로 128px 그림을 받아 그리는지로 바꿨다.

### 루프 8 — 연결이 끊겼을 때

**재현:** 오프라인으로 바꾼 뒤 할 일을 적거나 체크하면 화면 전체가 `app/error.tsx`
("잠깐 문제가 생겼어요")로 바뀌고 적던 글자도 사라졌다. 학생들이 지하철·복도에서
쓰는 앱이라 흔한 상황이다.

- `components/use-save-failure.ts`
  - `useSaveFailure()`: 실패를 잡아 알림(토스트) "저장하지 못했어요. 연결을 확인하고
    다시 해주세요."를 띄운다. 할 일 추가·체크·수정, 반응, 순서 바꾸기, 카테고리 수정에 썼다.
  - `orSaveFailure(action)`: useActionState 폼(일정, 루틴, 프로필, 닉네임, 계정 삭제)용.
    실패하면 폼의 안내 문구로 알린다.
  - 세션이 끊겨 서버가 `redirect("/login")`하면 클라이언트에서도 예외로 넘어온다
    (`server-action-reducer.js`에서 redirect 오류로 reject). 삼키지 않도록
    `unstable_rethrow`(next/navigation, 번들 문서 확인)로 Next에 돌려준다.
- 할 일 추가·수정 폼은 `<form action>` 대신 `onSubmit` + `useTransition`으로 바꿨다.
  React는 form action이면 성공·실패와 상관없이 입력칸을 비운다
  (`startHostTransition`이 액션 전에 `requestFormReset`을 예약한다). 이제 성공했을 때만 비운다.
- 순서 바꾸기가 실패하면 화면 순서를 서버 순서로 되돌린다.
- 체크·반응은 useOptimistic이라 실패하면 저절로 원래대로 돌아간다.

**재확인:** `tests/e2e/offline.spec.ts` 3개 — 끊긴 채 적기(글자 유지, 다시 연결 후 Enter로

남은 한계: useActionState 폼(일정·루틴 등)은 React가 입력칸을 비우는 건 그대로다. 문구로는

### 루프 10 — CI 재확인, 폼이 입력을 잃는 문제

**CI:** 최근 main CI가 계속 실패하고 있었다(배포는 Vercel이 따로 해서 성공). 실패는 매번
두 계정을 오가는 테스트(feed 반응, friend-day)의 `page.goto: Test timeout of 30000ms`.
같은 테스트가 개발 PC에서도 13~17초이고, CI는 러너(미국)↔DB(싱가포르) 왕복이 길어 전체가
2배 넘게 느리다(63개 16.8분). 앱 버그가 아니라 시간 예산 문제라 `playwright.config.ts`에서
**CI에서만** 테스트 제한 시간을 60초로 늘렸다. 확인하는 내용은 그대로다.
대기 중인 CI 실행이 "cancelled"로 보이는 건 `concurrency` 그룹이 대기열을 하나만 두기
때문이다(설정대로다).

**폼:** 루프 8에서 남긴 한계를 파다가 더 흔한 버그를 찾았다. `useActionState` + `<form action>`
폼은 **서버가 입력을 거절해도** React가 입력칸을 모두 처음 값으로 되돌린다. 루틴에서 요일을
안 고르고 추가하면 "요일을 골라주세요"와 함께 적은 내용이 사라졌고, 일정도 종료일이 잘못되면
이름이 사라졌다(임시 테스트로 재현: 입력값 `""`).

- `components/use-form-action.ts`의 `useFormAction(action, null)`: onSubmit으로 보내고,
  서버가 `ok: true`를 줄 때만 비운다. 연결 실패는 `orSaveFailure`로 문구를 띄우고,
  보내는 중 Enter를 또 누르면 무시한다.
- 일정·루틴·프로필·닉네임·계정 삭제 폼 5개에 적용. 루틴 성공 응답에 `ok: true` 추가.
- `SubmitButton`에 `pending` prop — onSubmit 폼은 `useFormStatus`가 보내는 중을 모른다.

**재확인:** `tests/e2e/form-keeps-input.spec.ts` — 루틴 거절 후 내용 유지 → 요일 고르고
다시 누르면 만들어지고 비워짐, 일정 날짜 오류 후 이름 유지. 기존 루틴·일정·프로필·계정·
로그인 테스트도 전부 통과.

검증: `npm run verify` 통과 — 단위 70×3, E2E 71/71.

### 루프 1 — 권한과 입력 검증

- 데이터를 바꾸는 38곳 전수 조사: 모두 `userId: user.id`로 내 것만 바꾸거나, 먼저 주인을 확인한다.
  읽기(피드·친구 화면·반응 보내기)도 "팔로우 중 + 완료 + 공개 카테고리"만 다룬다. 친구 화면은 일정을 넘기지 않는다.

- 고친 것: 되돌리기 스냅숏과 순서 목록처럼 브라우저가 돌려주는 id 목록에 모양·길이 검사가 없었다.

### 루프 3 — 날짜와 시간대

- `new Date()`는 모두 "지금 시각"을 기록하는 용도(doneAt, pausedAt 등)였다. 로컬 시간 함수(getDate, toLocaleString 등)는
  lib/date.ts 밖에 하나도 없다. 단위 테스트는 UTC·Asia/Seoul·America/New_York에서 돈다. VM(Asia/Seoul)으로 옮겨도 결과가 같다.
- 고친 것: 앱을 켜 둔 채 자정을 넘기면 아침에 다시 열어도 어제를 "오늘"로 보여주고, 거기 적은 할 일이 어제 날짜로 들어갔다.
  `components/day-rollover.tsx` — "오늘"을 보는 홈(주소에 ?date= 없음)에서 화면이 다시 보일 때와 1분마다 날짜를 비교해
  바뀌었으면 `router.refresh()`. 날짜를 골라 보는 화면에는 붙이지 않는다.
- `tests/e2e/day-rollover.spec.ts`: 가짜 시계로 하루 앞당기면 새로 그리는 요청이 가는지(고치기 전 코드로 돌려 실패 확인),
  날짜를 고른 화면은 그대로인지.

검증: `npm run verify` 통과 — 단위 73×3, E2E 75/75.

### 루프 4 — DB 성능

VM에 시험 DB(사용자 1000, 할 일 108만, 반응 24만, 280MB)를 만들어 Prisma가 실제로 만드는 SQL로 실행 계획을 쟀다.

| 쿼리 | 시간 | 비고 |
|---|---|---|
| 오늘 할 일 / 이번 달 / 연속 기록(1년) | 0.2 / 0.2 / 0.4ms | 인덱스 |
| 피드 첫 쪽(팔로우 10명) | 7ms | 사람마다 인덱스, top-N 정렬 |
| 안 읽은 반응 수(**매 요청**) | 9.8ms → **0.23ms** | 내 할 일 수에 비례하던 것 |
| 받은 반응 목록 | 46ms → **0.09ms** | 반응 테이블 전체를 훑던 것 |

- 고친 것: `Reaction.todoUserId` + `(todoUserId, createdAt)` 인덱스. 마이그레이션 `20260927120000_reaction_todo_user`가
  기존 행을 할 일에서 채운 뒤 NOT NULL로 바꾼다(24만 행 5초). 결정은 `docs/decisions.md`.
- 테스트 DB에 적용 후 `prisma migrate diff --exit-code`로 스키마와 차이 없음 확인.
