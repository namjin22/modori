# 장애·버그 기록

운영(또는 운영 배포)에 영향이 있었거나, 배포 시험에서 잡혀 운영에 나갈 뻔한 문제를 적는다.
테스트에서만 드러나 바로 고친 버그는 `docs/handoff.md`에 둔다.

같은 일이 다시 났을 때 "지난번엔 어떻게 했지"에 답하고, 재발 방지가 실제로 들어갔는지 확인하려고 남긴다.
증상을 겪는 동안 바로 적기 시작하고(시각이 가장 먼저 사라진다), 고친 뒤 나머지를 채운다.

## 양식

```markdown
### INC-<번호> <한 줄 요약> (<발생 날짜>)

- **영향**: 누가, 얼마나, 얼마 동안 (예: 운영 전체 / DataGSM 로그인 사용자 / 영향 없음 — 배포 시험에서 발견)
- **발견**: 어떻게 알았나 (사용자 제보, health 알림, errors 알림, 배포 실패, 직접 발견)
- **증상**: 사용자나 운영자가 본 것. 오류 원문이 있으면 그대로(토큰·쿠키·개인정보는 지운다)
- **원인**: 왜 그랬나. 추측이면 추측이라고 쓴다
- **조치**: 무엇을 했나. 커밋·PR 번호
- **재발 방지**: 다시 안 나게(또는 나면 바로 알게) 무엇을 바꿨나. 테스트·알림·규칙·문서. 없으면 "없음"과 이유
```

- 번호는 이어서 붙이고 지우지 않는다.
- 사용자의 이름·이메일·할 일 내용은 적지 않는다. 저장소가 공개다.
- "재발 방지"가 "조심한다"뿐이면 아직 안 끝난 것이다. 테스트나 알림처럼 사람이 잊어도 도는 것을 적는다.

## 기록

### INC-6 main에 합친 커밋이 검증 취소로 배포되지 않는다 (2026-09-29)

- **영향**: 없음 — 다음 main 커밋이 앞 커밋을 포함해 같이 배포됐다. 사용자에게 늦게 반영된 것뿐
- **발견**: 배포를 기다리다 `deploy-gsmsv`가 `skipped`로 끝난 것을 직접 확인
- **증상**: main에 합친 직후 다음 PR을 열자 main 검증(`verify`)이 `cancelled`가 되고, 검증 성공에 묶인 배포(`deploy-gsmsv`)가 그 커밋에서 `skipped`
- **원인**: 검증을 한 줄(`verify-shared-database`)에 세웠는데, GitHub는 기다리는 실행을 하나만 남기고 새 실행이 오면 앞의 대기를 취소한다.
  PR 검증이 main 검증을 밀어냈다. 이슈 #112(배포를 검증에 묶기)를 넣은 뒤에야 드러났다
- **조치**: main 검증과 PR 검증을 다른 줄로 나눴다. PR은 브랜치마다 줄을 나누고 같은 PR의 새 커밋만 앞 실행을 취소한다
- **재발 방지**: 워크플로 주석에 이유를 적었다. 자동 검사는 없다(워크플로 동작이라 실제 실행으로만 확인). 남은 위험은 backlog에 적었다

### INC-5 알림을 봐도 아래 소셜 탭의 알림 수가 사라지지 않는다 (2026-09-29 제보)

- **영향**: 알림을 받은 모든 사용자. 알림 수 뱃지가 도입된 뒤부터 2026-09-29 수정 배포까지. 새로고침하면 사라졌다
- **발견**: 운영자 제보
- **증상**: 소셜 → 알림을 열어 NEW를 확인하고 링크로 돌아와도 아래 탭의 숫자가 그대로 남았다
- **원인**: 알림 수는 탭 공통 레이아웃(`app/(tabs)/layout.tsx`)이 센다. Next App Router는 링크로 오갈 때 공통 레이아웃을
  다시 그리지 않아, 알림 화면이 읽은 시각을 갱신해도 레이아웃의 숫자는 처음 그린 값으로 남았다. 처음 불러올 때도 레이아웃이
  화면보다 먼저 숫자를 세서 같은 요청 안에서 갱신 전 값이 나왔다. 기존 E2E는 매번 `page.goto`로 새로 불러와 이 경로를 밟지 않았다
- **조치**: 알림 화면이 뜬 뒤 서버 액션(`markNotificationsSeen`)이 `revalidatePath("/", "layout")`로 레이아웃을 다시 그리게 했다.
  읽은 시각은 여전히 화면을 그릴 때 남긴다(바로 떠나도 읽은 것으로). 보는 동안 NEW가 사라지지 않게 처음 값을 붙잡았다
- **재발 방지**: 링크로만 오가며 뱃지가 사라지는지 보는 E2E(`tests/e2e/notification-badge.spec.ts`). 고치기 전 코드에서 실패하는 것을 먼저 확인했다

### INC-4 배포 스크립트가 DB가 켜지기 전에 마이그레이션을 돌리고, 고장 난 버전을 그대로 둔다 (2026-09-27)

- **영향**: 없음 — 운영에 나가기 전 배포 시험(포트·이미지를 운영과 분리)에서 발견
- **발견**: 직접 발견. 새 VM으로 복구하는 경우와 켜자마자 죽는 이미지를 흉내 내 시험했다
- **증상**: DB 컨테이너가 막 켜진 직후에는 마이그레이션이 실패해 첫 배포가 멈췄다. 새 버전이 응답하지 않아도
  배포는 실패로만 끝나고 고장 난 버전이 떠 있었다
- **원인**: 배포 스크립트가 DB 준비를 기다리지 않았고, 새 버전이 뜨는지 확인한 뒤 되돌리는 단계가 없었다
- **조치**: `docker compose up -d --wait db`로 DB 준비를 기다리고, 직전 이미지를 `modori:previous`로 남겨 60초 안에
  응답이 없으면 되돌린다(2026-09-27 커밋 "fix: 배포가 DB 준비를 기다리고, 새 버전이 뜨지 않으면 직전 버전으로 되돌린다")
- **재발 방지**: 되돌림 시험 방법을 `deploy/README.md`에 두고 출시 체크리스트 P0에 "배포 실패 시 직전 버전으로 되돌린다(시험 완료)"

### INC-3 운영에서 DataGSM 로그인이 되지 않는다 (2026-09-20)

- **영향**: DataGSM으로 로그인하려는 모든 사용자(Google 로그인은 정상). 2026-09-20 연결 배포부터 2026-09-21 수정 배포까지
- **발견**: 운영에서 DataGSM 로그인을 시도해 확인(사용자)
- **증상**: DataGSM 화면에서 아이디·비밀번호를 넣으면 `/api/auth/error?error=Configuration`(영어 "Server error" 화면)으로
  돌아왔다. Vercel 로그에는 콜백에서 `error: invalid_request`, 밖으로 나간 요청 없음(userinfo까지 가지 못함)
- **원인**: 두 가지였다(2026-09-21 요청을 직접 보내 측정). ① `checks: ["pkce"]`만 둬서 authorize 요청에 state가
  빠졌다. ② 토큰 요청을 JSON으로 바꾸는 코드가 Authorization 헤더를 지우는데 본문에도 자격 증명이 없어 어떤 인증도
  실리지 않았다. 토큰 엔드포인트는 JSON 본문 + 본문 자격 증명만 받는다(Basic 헤더 401, form 본문 415)
- **조치**: `checks: ["state", "pkce"]`, `client_secret_post`(2026-09-21 커밋 "fix: DataGSM 로그인의 state와 토큰 요청
  형식을 바로잡는다"). 배포 뒤 실제 로그인 성공 확인
- **재발 방지**: `lib/auth.ts`의 DataGSM 설정마다 왜 필요한지 주석을 달았다. 로그인 오류는 제공자 오류 코드를 남긴다
  (`logger.error`, 인가 코드는 버림). 실제 OAuth는 E2E로 시험할 수 없어 자동 검사는 없다

### INC-2 글꼴(Pretendard)이 운영에서 전혀 불러와지지 않는다 (2026-09-16)

- **영향**: 모든 사용자, 모든 화면이 시스템 글꼴로 보였다. 첫 배포부터 2026-09-16 수정까지
- **발견**: 빌드 경고
- **증상**: 화면 글꼴이 디자인과 달랐다. 오류는 없었다
- **원인**: `globals.css`의 `@import url(...)`가 Tailwind가 앞에 붙인 규칙 뒤로 밀렸다. 브라우저는 규칙 뒤의
  `@import`를 무시한다
- **조치**: `app/layout.tsx`의 `<link rel="stylesheet">`로 옮겼다(86e631e)
- **재발 방지**: 없음 — 빌드 경고를 읽는 것에 기댄다. 글꼴을 확인하는 테스트는 두지 않았다

### INC-1 Vercel 배포가 `prisma generate`에서 실패한다 (2026-09-16)

- **영향**: 배포가 막혔다(운영 중이던 버전은 그대로)
- **발견**: 배포 실패
- **증상**: `postinstall`의 `prisma generate`가 `CLI.UNKNOWN_COMMAND`로 실패
- **원인**: 버전을 정하지 않고 설치해 npm `latest` 태그의 `prisma@8.0.0-rc.15`가 깔렸고, `@prisma/client`는 7.10.0이라
  CLI와 client의 메이저 버전이 어긋났다. 8 RC CLI는 명령 체계가 다르다
- **조치**: CLI와 client를 둘 다 `6.19.3`으로 정확히 고정(b957ebb). 결정은 `docs/decisions.md` "Prisma는 6.x로 고정한다"
- **재발 방지**: CLAUDE.md "버전 주의"에 Prisma 6.x 고정 규칙, `package-lock.json`을 같이 커밋(배포는 `npm ci`)

## INC-7 매월 1~9일에 달력 테스트가 실패해 배포가 멈춤 (2026-10-01)

- **증상:** 10/1 00:14(KST) main verify가 실패해 PR #126 배포가 건너뛰어졌다. 운영 서비스에는 영향이 없다(직전 배포 유지).
- **원인:** `tests/e2e/calendar.spec.ts`가 오늘 칸을 `getByRole("link", { name: "1일, 완료 없음" })`로 찾는데, 문자열 이름은 부분 일치라 `11일`·`21일`·`31일`도 잡혀 strict mode 위반. 오늘이 1~9일이면 매번 난다. 9/30까지는 이름이 겹치지 않아 통과했다.
- **조치:** `exact: true`를 붙였다(3곳). 10/1에 전체 verify로 재현·통과를 확인했다.
- **재발 방지:** 날짜를 이름에 넣어 찾는 테스트는 정확히 일치로 찾는다. 사용자가 "필요한 테스트 수리는 승인 없이 해도 된다"고 했다(2026-10-01).

### INC-8 iPhone(Safari)에서 일정 만들기의 날짜 창이 열리지 않고 가입 경로가 빠질 수 있음 (2026-10-05 발견)

- **영향**: iPhone·Safari 사용자 중 일정 이름을 쓰기 전에 날짜 버튼을 누른 사람(날짜 창 배포 10/2부터). 제보는 없었고 정식 공개(10/6) 전날 발견했다.
- **발견**: 공개 전 점검에서 지금까지 Chromium(크롬)으로만 시험했다는 빈틈을 찾아, 핵심 흐름을 WebKit(iPhone 화면)으로 처음 돌렸다. 날짜 창 시험 4개가 WebKit에서만 실패했다.
- **증상**: 일정 만들기 칸에서 이름을 비운 채 시작일·종료일 버튼을 누르면 날짜 창이 열리기 전에 일정 칸이 닫혔다. 이름을 먼저 쓰면 열렸다. 같은 구조의 카테고리 추가 칸도 칸 안의 버튼을 누르면 닫힐 수 있었다.
- **원인**: "이름을 비운 채 다른 곳을 누르면 닫는" 코드가 포커스가 어디로 옮겨 갔는지(`relatedTarget`)로 "칸 밖"을 판단했다. Safari·iPhone은 버튼을 눌러도 버튼에 포커스를 주지 않고, 안쪽 창(날짜 고르기)이 닫힐 때도 포커스를 칸으로 돌려주지 않아 `relatedTarget`이 비어, 칸 안을 눌렀는데 밖으로 판단했다.
- **조치**: 칸 안에서 포인터가 눌린 직후(0.7초)의 포커스 이탈은 안쪽 조작으로 본다(`components/use-blur-outside.ts`, 일정·카테고리 추가 칸에 적용).
- **같이 찾은 것**: 가입 경로(`?from=`)를 화면 준비 뒤에 저장하는 방식이라, 느린 폰에서 스크립트가 준비되기 전에 로그인 버튼을 누르면 경로가 저장되지 않았다 → `<head>`에서 바로 도는 스크립트로 옮기고(`SOURCE_SCRIPT`), 가입 때도 제출하는 순간 읽도록 했다.
- **재발 방지**: `npm run test:webkit`(iPhone 화면 WebKit으로 폰 해당 시험 67개)을 추가했다. 공개 전·화면 동작을 크게 바꾼 뒤에 돌린다(속도 때문에 `verify`에는 넣지 않았다). WebKit 시험을 처음부터 돌려야 하는 이유와 뺀 시험의 까닭은 `playwright.webkit.config.ts`에 적었다. `SOURCE_SCRIPT`는 TypeScript 함수와 같은 입력으로 견주는 단위 시험이 있다.

### INC-9 가입 화면의 프로필 캐릭터 원이 칸 밖으로 삐져나옴 (2026-10-07, 정식 공개 당일 제보)

- **영향**: 가입 화면과 마이페이지의 프로필 사진 고르기를 보는 모든 사용자(캐릭터 프로필 배포 10/3부터). 가입은 정상으로 됐고 모양만 틀어졌다.
- **발견**: 공개 직후 운영자 제보(스크린샷).
- **증상**: 캐릭터 원(64px)이 칸(57px)보다 커서 옆 칸까지 겹쳐 보였다. 칸 폭이 넓은 화면에서는 생기지 않아 지금까지 스크린샷·자동 시험(좁은 가입 화면을 재지 않음)에서 놓쳤다.
- **원인**: 가입 화면 폭은 최대 336px인데 칸을 "화면 폭 420px 이상이면 5열"로 고정했다. 화면 폭(뷰포트)을 기준으로 열 수를 정해서, 실제 칸 폭(5열 → 57px)이 원보다 좁아졌다.
- **조치**: 열 수를 칸 폭 기준으로 바꿨다(`repeat(auto-fit, minmax(5rem, 1fr))`, 원 56px). 가입 화면 336px에서는 3열 + 2열이다.
- **재발 방지**: `tests/e2e/avatar-choice-size.spec.ts`가 폭 320·390·430·600px에서 원이 칸 안에 들어가고 칸끼리 겹치지 않는지 잰다. 고치기 전에는 430·600px에서 실패하는 것을 확인했다.
- **배포**: 시급해서 main 검증(35~40분)을 기다리지 않고 `deploy-gsmsv`를 수동 실행했다(로컬 `npm run verify` 단위 182×3·E2E 184/185, 1개는 홈 로딩 시간 초과로 재실행 통과). main 검증은 뒤따라 돈다.

### INC-10 가입(닉네임) 화면에 갇혀 다른 계정으로 로그인할 수 없음 (2026-10-07, 정식 공개 당일 제보)

- **영향**: 닉네임을 정하기 전의 계정으로 로그인한 모든 사람. 잘못 고른 구글 계정이면 다른 계정으로 바꿀 방법이 없었다.
- **발견**: 공개 직후 운영자 제보(스크린샷).
- **증상**: `/onboarding`에서 주소를 지우고 어느 화면으로 가도, 로그인 화면으로 가도 계속 이 화면으로 돌아왔다. 뒤로가기·로그아웃·계정 바꾸기 버튼이 없었다.
- **원인**: 가입을 마치지 않은 계정은 모든 탭 화면이 `requireUser`로 온보딩에 보내고, 로그인 화면은 로그인된 계정을 홈으로 보낸다(서로 다른 화면이 같은 기준을 쓰도록 만든 것, `lib/session.ts`). 그래서 닉네임을 정하지 않는 한 나갈 길이 없는데, 온보딩 화면에는 로그아웃 버튼이 없었다. 로그아웃은 마이페이지(탭 화면)에만 있었다.
- **조치**: 온보딩 화면 아래에 "로그아웃하고 다른 계정으로 로그인" 버튼을 넣었다(`leaveOnboarding`). 누르면 로그인 화면(`?switch=1`)으로 가고, Google은 이전 계정으로 바로 들어가지 않게 계정 선택 창(`prompt=select_account`)을 띄운다.
- **재발 방지**: `tests/e2e/auth.spec.ts`가 "온보딩에서 어디로 가도 돌아오지만 로그아웃으로 빠져나온다"를 확인한다. 로그인된 사람이 갈 수 있는 모든 화면에는 로그아웃 길이 있어야 한다는 점을 이 기록에 남긴다.
- **배포**: 시급해서 main 검증을 기다리지 않고 `deploy-gsmsv`를 수동 실행했다(로컬 `npm run verify` 통과 후).

### INC-11 일부 와이파이(ipTIME)에서 데스크톱 앱이 "연결하지 못했어요"만 띄움 (2026-10-07 제보)

- **영향**: 학교 와이파이가 아닌 다른 망(ipTIME 공유기)에서 데스크톱 앱을 쓰려던 사용자 1명(양은준 계정 쪽 제보). 학교 와이파이에서는 되었다. 웹 사이트와 서버는 정상이었다.
- **발견**: 사용자 제보(디스코드 대화 캡처).
- **증상**: 데스크톱 앱이 "모도리에 연결하지 못했어요 / 인터넷 연결을 확인해 주세요" 안내만 보였다. 어떤 오류인지 앱이 알려 주지 않아 원인을 알 수 없었다.
- **확인한 것**: 통신사 DNS(KT·SK·LG)와 1.1.1.1·8.8.8.8·9.9.9.9 모두 `modori.site`를 풀었고, IPv4·IPv6·HTTP/1.1로 모두 200이었다(서버·도메인은 정상). 그 사용자는 같은 날 다른 망에서 이용한 기록이 있다. 즉 서버가 아니라 **그 망에서 앱이 서버로 가는 길**의 문제다.
- **원인**: 확정하지 못했다(그 망에서 어떤 오류 번호가 났는지 모른다). 후보: 공유기 DNS가 이름을 못 푸는 경우, UDP 443(QUIC)·특정 IP를 막는 경우, 연결이 끊긴 와이파이. 앱의 안내 화면이 원인을 가리지 못해 추측할 수밖에 없는 것이 진짜 결함이다.
- **조치(데스크톱 1.0.3)**: ① 안내 화면에 오류 이름과 번호(예: ERR_NAME_NOT_RESOLVED -105)와 원인별 안내(DNS·차단·시간/보안 연결)를 보여 준다. ② 앱에서는 QUIC(HTTP/3)을 끄고 TCP(HTTPS)만 쓴다(막는 망에서 지연·끊김을 피하는 가설 조치, 모도리는 TCP로 충분하다).
- **재발 방지**: 같은 일이 또 나면 사용자가 화면의 오류 이름을 알려 줄 수 있어 원인이 가려진다(`tests/e2e/desktop-app.spec.ts`가 닫힌 포트로 오류 이름 표시를 확인). 데스크톱 앱은 자동 업데이트가 없어 사용자가 1.0.3을 새로 받아야 한다(알고 있는 한계, backlog).

### INC-12 시간대 설정을 배포했는데 캐나다 사용자의 날짜가 여전히 하루 어긋남 (2026-10-08 제보)

- **영향**: 서울이 아닌 곳에 사는 사용자(제보는 캐나다 1명). 코드의 오작동이 아니라 설정을 못 찾아 서울 기본값으로 남아 있었다.
- **발견**: 사용자 제보("날짜가 아직 다음 날로 넘어간다"). 운영 DB를 읽어 보니 시간대를 바꾼 사용자가 한 명도 없었다(73명 전원 Asia/Seoul).
- **증상**: 시간대 설정 배포(10/8) 뒤에도 해외 사용자의 "오늘"이 서울 기준으로 하루 어긋났다.
- **원인**: 기능은 마이페이지 안쪽의 설정이라 해외 사용자가 존재를 모르고, 기본값은 서울이었다. 기능을 만들고 "찾아서 바꿔 달라"고 안내하는 것에 기댄 설계 결함이다.
- **조치**: ① 기기 시간대가 저장된 시간대와 다르면(목록에 있을 때) 탭 화면 맨 위에 "이 기기는 ○○ 시간이에요. 맞출까요?" 카드를 띄운다("맞추기"/"지금 그대로", 그대로를 누르면 그 기기 시간대에는 다시 묻지 않음). 자동으로 바꾸지 않는다. ② 새로 가입하는 사람은 기기 시간대가 기본으로 저장된다. ③ 시험을 돌리는 브라우저 시간대를 서울로 고정했다(`playwright.config.ts`).
- **재발 방지**: `tests/e2e/timezone.spec.ts`가 기기 시간대를 토론토로 바꿔 안내 카드·맞추기·그대로·가입 기본값을 확인한다. 새 설정을 만들 때는 "누가 이 설정을 찾는가"를 같이 설계한다는 점을 이 기록에 남긴다.
