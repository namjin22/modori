5. **첫날에 대부분 정해졌고 그 뒤로는 거의 늘지 않았다.** 10/7 가입자 가운데 할 일을 가진 사람은 10/14 기록 6명 → 오늘 7명이다. 하루 합계의 `withTodo`도 10/7 하루 동안 8 → 15(+7)로 늘고 10/14까지 19로 완만했다(옛 가입자가 섞였을 수 있다).

포트폴리오에는 "효과를 증명했다"가 아니라 이렇게 쓰는 것을 권한다: **공개 첫날 데이터에서 가입자 40명 중 5명만 할 일을 쓴 것을 보고(13%), 새 계정으로 첫 화면을 찍어 원인(입력칸을 찾기 어려움)을 확인했고, 그날 저녁 작은 변경으로 고쳤다. 개선 뒤 가입자가 9명뿐이라(22%, 구간 6~55%) 효과는 판단을 보류했다.**

**다시 세는 법**: 부록 A의 쿼리 2. 가입 시각으로 세 집단(공개 전 / 공개 뒤·개선 전 / 개선 뒤)을 나누고, "한 번이라도 썼는가"와 "가입 뒤 7일 안에 썼는가"를 같이 센다. 7일 안 비율은 지켜본 기간 차이(4번 이유)를 없앤다. 그 결과도 집단마다 10명 안팎이면 "표본이 작아 결론을 내지 않는다"가 맞는 결론이다.

### 2-4. 재방문(가입 뒤 7일 안에 다시 온 비율)

**정의**(`lib/metrics.ts`의 `cohortOf`, `docs/metrics.md`): 어느 날 가입한 사람 가운데 **다음 날부터 7일 안에** 하루라도 다시 쓴 사람의 비율. 날짜는 서울 기준.

출처는 하루 합계 CSV의 `cohortSize`·`cohortReturned`다. 어느 날 줄에는 **7일 전에 가입한 사람**의 값이 들어 있다(10/14 줄 = 10/7 가입자). 시연 계정(10/15 가입 2명)은 뺐다.

| 가입 집단 | 가입 | 7일 안에 다시 씀 | 비율(구간) |
|---|---|---|---|
| 공개 전(가입일 9/28~10/5) | 21 | 12 | 57%(37~76%) |
| 공개 뒤(10/6~) | 52 | 15 | 29%(18~42%) |
| └ 10/7 하루(디스코드 유입이 대부분) | 42 | 9 | 21%(12~36%) |
| └ 나머지 날짜 합(디스코드 1, 직접 4, 앱 5) | 10 | 6 | 60%(31~83%) |

- 10/7 하루(21%)와 나머지(60%)의 차이는 Fisher 정확 검정으로 p = 0.024다. 하지만 두 집단의 가입 경로가 다르고 나머지가 10명뿐이라 그대로 읽을 수 없다. 공개·개선 방식의 효과가 아니라 **어디서 온 사람이냐**의 차이일 가능성이 크다 [추정].
- 기간 제한 없이 한 번이라도 다시 쓴 사람(사용자별 CSV, 쓴 날 2일 이상): 공개 전 가입자 20명 중 14명(70%), 10/7 가입자 41명 중 10명(24%), 10/8 이후 9명 중 5명, 10/6 1명 중 1명 [측정].
- **이전 기록과 다르다.** 10/7 가입자는 [기록 10/14] 41명 중 6명(15%)이었는데, 하루 합계 10/14 줄은 42명 중 9명(21%)이다. 하루 합계는 그날이 끝난 뒤의 값이라 이쪽을 쓴다. 기록한 시각과 분모(41·42)가 다른 이유는 문서로 확인하지 못했다 [미확인]. 낮에 센 값이라 7일 창이 덜 찼을 것으로 본다 [추정].
- 10/7 가입자를 행동으로 나눈 관찰: 할 일도 팔로우도 안 한 34명 중 다시 온 사람은 3명, 둘 다 한 2명은 2명 모두 다시 왔다 [기록 10/14]. 2명이라 결론이 아니라 관찰이다.
- 공개 전 집단은 지인·시험 계정이라 동기가 다르다. 가입일은 9/28이 12명으로 가장 크다(지표 수집을 시작한 날이다).
- [기록 10/3]의 "최근 7일 쓴 사람 20 / 가입자 20"은 재방문율이 아니다(가입 직후 쓴 날도 들어간다).

## 5. CI/CD를 측정으로 줄인 기록

> 포트폴리오·면접용 정리. 자세한 결정 기록은 `docs/decisions.md`("CI를 쪼개고 시험 DB를 러너 안으로 옮긴다",
> "CI/CD를 측정으로 다시 짠다", "Playwright 글꼴 .deb 캐시"), 숫자와 운영 메모는 `docs/ci-cd.md`에 있다.
> 숫자는 2026-11-24 기준(11-23·24 개선까지)이다. 1절의 시험 수와 센 날이 달라 조금 다르다(94개 파일·약 360개 ↔ 96개 파일·378개).


### 한 줄 요약

GitHub Actions 파이프라인을 **단계별로 재서 병목을 찾고, 가설마다 실험 PR로 확인한 뒤** 바꿨다.
PR 검증은 **67분 → 약 3분**, 병합부터 운영 반영까지는 **약 8분 → 약 3분**, 문서만 바꾼 변경은 **약 14분 → 약 40초**가 됐다.
검증을 건너뛰는 규칙은 "틀려도 시간 낭비까지만" 되도록, 확신이 없으면 전부 돌리게 설계했다.

### 프로젝트와 환경

- **모도리**: 친구와 함께 쓰는 투두 서비스. Next.js 16(App Router) + Prisma + PostgreSQL 18, 웹·데스크톱(Electron)·모바일(Capacitor).
- **CI**: GitHub Actions(공개 저장소, 표준 러너 4 vCPU·16GB 실측). 타입 검사·린트·단위 시험(3개 시간대) + Playwright E2E 시험 파일 94개(약 360개 시험).
- **CD**: main의 검증이 성공한 커밋만 Docker 이미지로 만들어 학교 서버 VM에 SSH로 보낸다(배포 열쇠는 배포 스크립트만 실행하게 묶여 있다).

### 문제

| 시점 | PR 검증 | 무엇이 문제였나 |
|---|---|---|
| 2026-11-19 전 | **67분** | E2E 358개를 한 줄로(워커 1). 미국 러너에서 싱가포르의 공용 시험 DB로 질의마다 왕복 |
| 2026-11-19 ~ 11-23 | 352초(최근 20회 중앙값) | 같은 시험을 PR과 main에서 두 번 돌려 PR을 열고 운영에 뜨기까지 약 14분. 문서 한 줄 고쳐도 같다 |

### 접근: 추측하지 않고 쟀다

1. Actions API로 **작업·단계마다 걸린 시간**을 뽑아 표로 봤다.
2. 가설마다 **실험 PR**(병합하지 않음)을 열어 같은 코드에서 변수 하나만 바꿔 비교했다(워커 1·2·3 × 조각 4개, 균형 배치 6·8조각, 설치 캐시, Docker 빌드 캐시, 시스템 패키지).
3. 시험 파일별 시간을 JSON 리포터로 뽑아 조각 나누기의 입력(가중치)으로 썼다.

측정으로 드러난 것: 병목은 "시험이 느리다"가 아니었다.

- **조각 불균형**: Playwright `--shard`는 시험 **개수**로 나눠 조각 4개의 시험 구간이 107~245초로 갈렸다. 가장 느린 조각이 전체를 정한다.
- **반복 설치**: 작업마다 `npm ci` 45~74초.
- **중복 검증**: PR에서 통과한 똑같은 코드를 main에서 다시 360초.
- **들쭉날쭉한 꼬리**: 브라우저용 시스템 패키지(글꼴 9개)를 apt로 받는 단계가 조각마다 7~71초. 조각이 8개면 거의 매번 하나가 걸린다.

### 해결

#### 1단계(11-19): DB를 러너 안으로, E2E를 4조각으로 — 67분 → 약 6분
운영과 같은 `postgres:18-alpine`을 러너 안 서비스 컨테이너로 띄워 질의 왕복을 없애고, E2E를 4개 작업으로 동시에 돌렸다.

#### 2단계(11-23): 측정 기반 재설계 — PR 352초 → 190초, 병합→운영 약 8분 → 176초
- **시간 기준 균형 배치(8조각)**: 파일별 실측 시간으로 무거운 파일부터 가장 가벼운 조각에 넣는다(LPT). 모든 조각이 같은 계산을 하므로 겹치거나 빠지는 파일이 없고,
  가중치에 없는 새 파일은 평균 무게로 친다. 조각 시험 구간이 91~102초로 고르게 됐다.
- **`node_modules` 캐시**: 설치 74초 → 15초. 캐시 안의 Prisma 클라이언트가 스키마보다 낡을 수 있어(락 파일은 같고 스키마만 바뀐 경우) 적중해도 클라이언트는 다시 만든다.
- **같은 코드 묶음은 다시 검증하지 않는다**: PR 검증이 끝까지 통과하면 `verified-<git tree 해시>` 표식을 남기고, main은 합쳐진 결과의 tree 해시로 그 표식을 찾는다.
  커밋 번호가 아니라 **파일 내용의 해시**가 같을 때만 건너뛰므로, 기준 브랜치가 그 사이 움직였으면 자동으로 전부 돌린다. main 검증 360초 → 58초.
- **문서만 바뀐 변경**: 시험과 배포를 건너뛴다(마지막 성공 배포와 비교). 문서 PR은 PR→운영 반영까지 약 42초, 운영 재기동도 없다.

#### 3단계(11-24): 시스템 패키지 캐시로 꼬리 자르기 — 시스템 패키지 단계 7~71초 → 2~8초
받아 둔 글꼴 `.deb`를 캐시해 `dpkg`로 바로 깐다. 캐시 키는 "러너 이미지 판 + Playwright 판"이라 같은 조합에서 이미 확인한 묶음이면 다시 묻지 않고,
이미지 판이 바뀌면 앞 판의 캐시로 먼저 해 본 뒤 Playwright에게 빠진 것이 없는지 확인한다. 하나라도 어긋나면 예전 길(apt)로 깐다.
시스템 패키지 단계는 7~71초에서 2~10초가 됐지만, 전체 검증 시간의 이득은 약 10초로 작았다(190·200초 → 178·194초). 남은 편차는 시험 구간 자체와 작업이 시작되기까지의 시간이다. 이것도 그대로 적는다.

### 신뢰성: 건너뛰기가 틀리면 검증 안 된 코드가 나간다

속도를 위해 검증을 건너뛰는 것은 안전을 거는 일이라, **틀렸을 때의 손해를 "시간 낭비까지"로 묶는 것**을 원칙으로 했다.

- 판단 스크립트의 어느 단계든 실패하면(API 오류, 기준 커밋을 못 가져옴, PR의 부모가 둘이 아님) 전부 돌린다.
- 표식의 이름만 믿지 않고, 표식을 남긴 실행이 이 저장소의 검증을 PR로 돌려 **성공**했는지 실행 기록에서 다시 본다.
- "문서만 바뀌면 시험 결과가 안 바뀐다"는 전제를 **시험으로 고정**했다(코드가 문서를 읽기 시작하면 그 시험이 먼저 깨진다. 임시 파일로 위반을 만들어 잡히는 것을 확인했다).
- 조각 나누기도 시험한다. 조각마다 따로 계산하는 방식이라, 이 시험이 없으면 어떤 파일이 한 번도 안 돌아도 CI가 초록색이다.
- 시스템 패키지 캐시는 형식을 알아볼 때만 빠른 길을 탄다. 글꼴이 빠진 채 시험이 돌면 한·영·일 화면의 글자 폭이 달라지기 때문이다.
- 시험 코드와 시험 환경은 바꾸지 않았다.

| 시스템 패키지 설치 빼기 | 브라우저는 뜬다 | 빠지는 9개가 전부 글꼴(한글·일본어 포함). 시험 환경이 바뀐다 → 빼지 않고 캐시했다(3단계) |
| main 재검증을 브랜치 보호에 맡기기 | | 설정과 사람의 규율에 기댄다. 내용이 같은지를 스스로 확인하는 쪽(tree 해시)을 골랐다 |

### 배운 점

- **평균이 아니라 꼬리**: 조각을 늘리면 "가장 느린 하나"가 전체를 정한다. 평균 10초짜리 단계도 8개 중 하나가 70초면 그게 검증 시간이다.
- **캐시는 무엇이 낡을 수 있는지부터**: `node_modules` 캐시는 생성된 Prisma 클라이언트를, 시스템 패키지 캐시는 러너 이미지 판을 함께 낡게 만든다. 실험의 "불러와진다"는 확인으로는 못 잡는 문제였다.
- **건너뛰기는 증거로**: "같은 코드"를 커밋이나 PR 번호가 아니라 내용의 해시로 정의하니, 예외 상황(기준 브랜치가 움직임, 재실행, 오래 열린 PR)이 따로 규칙 없이 안전한 쪽으로 떨어졌다.
- **버린 것도 기록**: 효과가 없던 시도를 숫자와 함께 남기면 같은 길을 다시 가지 않는다.

### 이력서에 쓸 문장(후보)

- GitHub Actions CI를 단계별 실측으로 분석해 E2E 조각을 시험 개수가 아닌 **실측 시간 기준으로 균형 배치**하고 의존성·시스템 패키지를 캐시해, PR 검증 시간을 **5분 52초 → 약 3분(약 −50%)**으로 단축
- PR에서 통과한 코드와 **git tree 해시가 같으면 main 재검증을 생략**하는 구조를 설계해, 병합부터 운영 반영까지 **약 8분 → 약 3분**, 문서 변경은 **약 14분 → 약 40초**로 단축(판단 실패 시 전체 검증으로 되돌아가는 fail-safe)
- 검증 생략의 전제(시험이 문서를 읽지 않음)와 조각 분할의 완전성(모든 시험 파일이 정확히 한 번 실행)을 **단위 시험으로 고정**해 CI 최적화가 시험 누락으로 이어지지 않게 함

### 면접에서 나올 질문과 답

**Q. 왜 워커를 늘리지 않고 조각(작업)을 늘렸나?**
워커를 2·3으로 늘리면 더 빨랐지만(245 → 148 → 128초) 불안정 시험이 0건에서 2건으로 늘었다. 같은 러너에서 CPU를 나누면 시험 사이의 경쟁이 드러난다.
조각을 늘리면 러너가 따로라 경쟁이 없고, 시간 기준으로 나누면 비슷한 이득을 얻는다. 시험을 고쳐서 워커를 늘리는 것은 다음 단계로 남겼다.

**Q. main 검증을 건너뛰면 위험하지 않나?**
같은 코드를 두 번 검증하는 것만 건너뛴다. "같다"는 git tree 해시(파일 내용 전체의 해시)로 정의해서, 기준 브랜치가 그 사이 움직였으면 해시가 달라 전부 돌린다.
대가는 있다: 같은 코드라도 날짜·러너 이미지 변화로 깨지는 시험은 이제 다음 PR이 잡는다(실제로 연도 경계 날짜 시험이 하루 만에 깨진 적이 있다). 이 대가를 결정 기록에 남겼다.

**Q. 캐시가 낡은 값을 주면?**
캐시마다 "무엇이 낡을 수 있는지"를 먼저 정했다. `node_modules`는 락 파일 해시로 키를 잡되 Prisma 클라이언트는 매번 다시 만든다.
시스템 패키지는 러너 이미지 판까지 키에 넣고, 판이 바뀌면 Playwright에게 빠진 것이 없는지 확인한 뒤에만 쓴다.

**Q. 효과를 어떻게 확인했나?**
개선 전은 최근 20회의 중앙값, 개선 후는 실행 번호가 남은 실측으로 적었다. 표본이 작은 값은 그렇다고 표시했다.
실험은 병합하지 않는 PR에서 같은 코드·같은 조각에 변수 하나만 바꿔 비교했다.

## 6. 면접에서 풀 만한 판단

공개 이후의 판단 3개(6-1~6-3)는 상황 / 선택지 / 고른 이유 / 포기한 것 / 결과로 적었다. 공개 전에 정리한 이야기 소재는 6-4, CI/CD는 5절 끝의 질문과 답에 있다.

### 6-1. 홈은 한 달치를 한 번에 받아 두고, 날짜는 브라우저에서 바꾼다 (2026-10-12)

- **상황**: 공개 뒤 디스코드에서 "날짜를 누를 때마다 0.몇~몇 초 로딩된다"는 제보가 왔다. 먼저 가까운 날을 미리 받게 해서 로컬에서 0.86~1.4초를 0.05~0.08초로 줄였다 [기록]. 그래도 먼 날짜와 처음 누르는 칸은 서버를 다녀왔고, 화면 하나를 열 때 이웃 날짜를 6~8번 더 그렸다.
- **선택지**: ① 미리 받기를 유지한다 ② 보이는 달 한 달치(할 일·반응·일정·루틴)를 한 번에 받고 달 안의 날짜 이동은 브라우저가 그린다 ③ ②에 앞뒤 달까지 받는다.
- **고른 이유(②)**: 한 사람의 한 달치는 수십~수백 줄이라 한 번에 보내도 가볍다. DB 질의가 날마다 7번이던 것이 한 달에 6번 안팎으로 준다. ③은 반응·이름까지 석 달치를 매번 보내는데, 달을 넘기는 일은 날짜를 고르는 일보다 드물다.
- **포기한 것**: 홈 화면 전체가 브라우저 쪽 컴포넌트가 되어 첫 화면의 자바스크립트가 늘었다. 다른 달로 가면 그 달을 받는 동안 기다린다. 지난 날의 루틴 할 일은 그 날을 열 때 만들어서 잠깐 "예정"으로 보인다(한 달치를 받을 때 다 만들면 열지 않은 날의 미완료가 쌓여 완료율이 틀어진다).
- **결과**: `tests/e2e/home-month.spec.ts`가 같은 달 안에서 날짜를 바꿀 때 서버 요청이 0번인지 지금도 CI마다 확인한다. 같은 방식을 친구 화면에도 넣었다. 한 달치 방식으로 바꾼 뒤 운영에서 체감 속도를 잰 기록은 없다 [미확인].

### 6-2. 목표 기능을 하루 만에 걷어내고 "할 일 밑 세부 할 일"로 다시 만든다 (2026-11-19~20)

- **상황**: 선배의 제안("최종 목표 아래 세부 목표")을 운영자가 전했다. 11-19에 개발을 맡은 AI는 "할 일에 하위 할 일을 단다"를 버리고 따로 목표 기능을 만들어 배포했다. 다음 날 운영자가 시안 그림과 함께 "내가 말한 건 할 일 밑의 작은 꼬리"라고 했다.
- **선택지**: 세부 할 일의 날짜(큰 할 일과 늘 같은 날 / 각자 날짜), 큰 할 일 체크(따로 / 세부를 다 끝내면 자동), 이미 만든 목표 데이터(코드만 걷기 / 표·열까지 지우기 / 큰 할 일로 옮겨 담기).
- **고른 이유**: 같은 날·따로 체크·표까지 지우기. 원한 것은 목록 안에서 큰 일을 쪼개는 것이라 같은 날이 가장 단순하다. 자동 완료는 친구 피드와 알림에 "끝냈다"가 저절로 뜬다. 안 쓰는 표를 남기면 개인정보 목록이 거짓이 된다.
- **포기한 것**: 며칠에 걸친 큰 목표(한 달짜리 프로젝트)는 못 담는다. 목표의 기한·공개 설정과 사용자가 만든 목표 데이터가 영구히 사라졌다(개수는 확인하지 못했다 [미확인], 복구는 VM 백업 7일 안에서만). 큰 할 일을 옮기면 끝낸 세부 할 일은 그 날에 남아 떨어진다.
- **결과**: 두 번에 나눠 배포했다. 첫 배포는 새 열을 더하고 목표 코드만 걷었다(되돌려도 옛 코드가 표를 찾는다). 그 배포가 정상이고 백업이 신선한 것(`/api/health` 200, 백업 `ageHours` 6)을 확인한 뒤 둘째 배포에서 표와 열을 지웠다(사용자 데이터 삭제라 운영자 승인). 세부 할 일은 그 뒤 AI 연결·AI 도우미·루틴 할 일·Android 위젯·할 일 창의 따로 넘어가는 화면(11-24)까지 이어졌다. 사용량은 [미확인].

### 6-3. 백업 사본 복원을 "스키마 통째로 바꾸기"로, 감시는 "복원 성공"에 건다 (2026-11-22)

- **상황**: VM 밖 백업 사본(Neon) 복원이 10-27부터 매일 오류를 냈는데 27일 동안 아무도 몰랐다(INC-23). `pg_restore --clean`은 덤프에 있는 표만 지워서, 운영에서 지운 표가 사본에 남아 `User`를 지우지 못했다. 감시는 VM 안 덤프 파일의 날짜만 봐서 복원 실패를 못 잡았다.
- **선택지**: 복원은 ① `public` 스키마를 비우고 채우기 ② 남은 옛 표만 손으로 지우기 ③ 표마다 CASCADE ④ 새 데이터베이스에 복원하고 이름 바꾸기. 감시는 ⓐ 복원 성공 표시 파일 ⓑ Neon에 접속해 행 수 비교 ⓒ 실패 메일.
- **고른 이유(①·ⓐ)**: ②·③은 다음에 표를 지울 때 같은 일이 또 나거나 스크립트를 또 손봐야 한다. ④는 Neon 무료 프로젝트에서 되는지 확인하지 못했다. ①을 한 트랜잭션으로 하면 실패해도 지난 사본이 그대로 남고, 사본이 늘 운영과 같은 모양이 된다. ⓑ는 Neon 비밀을 운영 앱에 둬야 하고, ⓒ는 메일 서비스가 새로 필요하다.
- **포기한 것**: 새 방식을 실제 PostgreSQL에서 미리 돌려 보지 못했다(이 PC에 Docker·psql이 없다. 첫 실행은 운영자가 VM에서 봤다). 감시는 복원이 끝까지 됐는지만 보고 사본의 내용(행 수)은 비교하지 않는다. VM의 `backup.sh`는 배포가 올리지 않아 운영자가 손으로 바꿔 넣었다.
- **결과**: 11-23 VM 반영 뒤 수동 실행이 성공했고, 11-24 04:00 자동 실행도 성공했다(13:30 KST `/api/health/backup` = `{"status":"ok","of":"restore","ageHours":10}`) [측정].

### 6-4. 공개 전에 풀 만한 이야기 (2026-10-04 정리)

- **한 가지 브라우저로만 시험하던 구멍**: 공개 전날 iPhone(WebKit)으로 처음 돌려 Safari에서만 생기는 버그를 찾았다(INC-8). 버튼을 눌러도 포커스가 안 오는 Safari 특성 때문에 일정 칸이 날짜 창을 여는 순간 닫혔고, 가입 경로 저장은 느린 폰에서 누락될 수 있었다. 고친 뒤 `npm run test:webkit`을 남겼다.
- **장애 8건과 재발 방지**: 배포 스크립트가 DB보다 먼저 마이그레이션을 돌린 문제(INC-4), 검증이 취소되면 배포가 빠지는 문제(INC-6), 매월 1~9일에만 깨지는 달력 테스트(INC-7).
- **빠르게 느껴지는 법**: 서버를 늘리지 않고 원인을 재서(VM 한가함 → 요청 왕복이 원인) 탭 미리 받기·체크 즉시 이동을 했다. 한 번은 전역 캐시를 켰다가 가입 직후 온보딩에 갇히는 버그를 E2E가 잡아 되돌렸다(`decisions.md`).
- **빌드 경고를 흘려보내지 않기**: 백업 감시를 만들다가 로컬 빌드에서 "프로젝트 전체를 서버 번들에 넣는다"는 경고가 떴고, 공식 안내대로 고쳤다. 운영 이미지를 직접 열어 보니 운영은 원래 영향이 없었다는 것까지 확인해 기록을 바로잡았다.
- **프라이버시를 지킨 지표 설계**: 화면별 이동 기록 대신 가입 단계·쓴 날짜만 센다. 이유와 대가를 문서로 남겼다(`metrics.md`).
- **테스트를 고쳐 통과시키지 않는 규칙**: 테스트가 실패하면 구현을 고친다. 동작이 바뀌어 고친 테스트는 요청 기록에 이유를 적었다.

- 서버가 학교 VM 한 대(2 vCPU / 4GB)다. 11-18 정전 재부팅으로 사이트 전체가 멈췄고(INC-22), 이런 일은 모도리 쪽에서 막을 수 없다. 장애 때 모도리 오류 화면을 띄우는 Cloudflare Worker는 만들어 뒀지만 켰는지는 [미확인]이다(운영자 몫). *(공개 뒤 새로 생김)*

- 용량의 근거가 오래됐다. 마지막 부하 시험은 2026-09-27(초당 약 50화면에서 CPU가 차고, 동시 100~150명까지 1초 안팎, `docs/capacity.md`)이고, 그 뒤 AI 도우미·일기·위젯·웹 푸시 등이 늘었지만 다시 재지 않았다.
- 의존성 보안 점검이 자동이 아니다(INC-19). *(새로 드러남)*

**시험·품질**
- CI의 E2E는 Chromium 하나다. iPhone WebKit 76개는 사람이 따로 돌리고, 실기기 자동 시험은 없다. 그래서 "실기기 확인 전"으로 반영한 요청이 있고, iPhone 위젯은 아직 아무도 실기기에서 보지 못했다.
- main에서 같은 코드를 다시 검증하지 않는다. 날짜·외부 변화로 깨지는 것은 다음 PR이 잡는다(`docs/ci-cd.md`). *(11-23 새로 생김)*
- 여러 줄 메모가 DB에 `\r\n`으로 저장된다(11-24 발견, 고치지 않음). 화면은 같고 AI 연결로 읽으면 보인다. *(새로 드러남)*

**지표**
- 화면별 이탈·체류 시간은 세지 않는다(개인정보를 덜 모으려는 선택, `docs/metrics.md`).
- 운영자 본인과 시연 계정 2개가 숫자에 들어 있고, 지운 계정·할 일은 빠진다. 날짜는 모두 서울 기준이다.
- 쓴 날짜는 90일만 남아, 공개 전 가입자의 재방문 원자료가 2026-12-15부터 지워지기 시작한다(7일 재방문 값은 하루 합계에 남아 있고 2-4에 옮겼다).
- 운영 숫자는 운영자 화면이나 VM에서만 볼 수 있다. 이번에는 운영자가 내려받은 CSV 두 개로 셌고, 10/7 배포 시각 전후 비교처럼 CSV로 답할 수 없는 것은 [미확인]으로 남았다.

**기능·플랫폼**
- Google Play 정식 출시를 못 했다. 프로덕션 액세스 신청이 두 번(10-30, 11-17) "추가 테스트 필요"로 돌아왔고 테스터는 12명이다. 다음 신청은 12/1쯤.
- iOS는 학교 Apple 계정이라 내부 테스팅을 쓰지 않고, 외부 테스트(베타 심사를 거침)만 쓴다(`docs/mobile-release.md`). 맥 앱은 없다(Safari "Dock에 추가" 안내).
- AI 도우미: Cloudflare Workers AI 무료 한도는 **전체 사용자 합산**(하루 10,000 뉴런, 요청 크기를 가정한 추정으로 gpt-oss-120b 약 77회)이고, 한 사람 하루 10번이다. 답이 느리고 스트리밍이 없다.
- AI 연결(MCP)은 접근 토큰 방식뿐이다(Claude 웹·앱 커넥터용 OAuth 없음). "모든 권한" 토큰은 프롬프트 주입에 속은 AI가 지우기·팔로우·반응까지 할 수 있다(`docs/mcp.md` "위험과 한계").
- 일기에 사진이 없다(저장소를 정하기 전).
- 세부 할 일은 큰 할 일과 같은 날에만 있어 며칠에 걸친 목표를 못 담고, 따로 옮길 수 없다.
- 데스크톱 앱: 관리자 권한이 걸린 PC에서 업데이트가 안 된 제보의 원인을 아직 모른다(INC-18 2차, 다음 제보 때 `updater.log`를 받는다).

**공개 전(10/04)의 한계 중 해결된 것**
- CI 검증 35~40분 → PR 약 3분(178·194초, 5절).
- 시험이 운영 DB를 같이 쓰던 문제 → GSMSV로 옮기며 분리, CI는 러너 안 Postgres.
- Vercel·Neon 무료 한도(하루 150~200명) → GSMSV로 옮겨 해당 없음.
- 백업 사본이 불완전하던 문제(INC-23) → 11-23 고침, 11-24 자동 실행 확인.

## 부록 A. 운영 숫자 쿼리

CSV로 답할 수 없는 것(10/7 18:22 배포 시각 전후로 나눈 활성화, 루틴이 만든 것을 뺀 할 일 수)과, 2-4의 재방문을 다른 정의로 다시 세는 데 쓴다.

VM에서 운영 DB에 돌린다(`deploy/README.md`의 다른 DB 명령과 같은 방식).

```bash
docker compose exec -T db psql -U modori -d modori < portfolio-metrics.sql
```

DB의 시각 열은 UTC(시간대 없는 timestamp)라 한국 시각으로 바꿔 센다. 개선 배포 끝 시각은 `2026-10-07 09:22:32 UTC`(18:22 KST), 공개일 시작은 `2026-10-05 15:00 UTC`(10/6 00:00 KST)다. 시연 계정(`signupSource = 'demo'`)은 뺀다.

```sql
-- 1. 오늘 운영 지표
SELECT
  (now() AT TIME ZONE 'Asia/Seoul') AS "기준_KST",
  (SELECT count(*) FROM "User") AS "계정",
  (SELECT count(*) FROM "User" WHERE nickname IS NOT NULL) AS "가입자",
  (SELECT count(*) FROM "User" WHERE nickname IS NOT NULL AND "signupSource" IS DISTINCT FROM 'demo') AS "가입자_시연계정_뺌",
  (SELECT count(DISTINCT "userId") FROM "ActiveDay"
     WHERE date BETWEEN (now() AT TIME ZONE 'Asia/Seoul')::date - 6 AND (now() AT TIME ZONE 'Asia/Seoul')::date) AS "최근7일_쓴_사람",
  (SELECT count(*) FROM "Todo") AS "할일_남아있는_전체",
  (SELECT count(*) FROM "Todo" WHERE "routineId" IS NULL) AS "할일_직접_적은_것",
  (SELECT count(*) FROM "Follow") AS "팔로우",
  (SELECT count(*) FROM "Reaction") AS "반응";

-- 2. 활성화: 가입 뒤 할 일(루틴이 만든 것 제외)을 쓴 비율. 가입한 지 7일이 안 된 사람은 뺀다.
WITH u AS (
  SELECT id, "createdAt",
    CASE
      WHEN "createdAt" < TIMESTAMP '2026-10-05 15:00:00' THEN '1 공개 전(~10/5)'
      WHEN "createdAt" < TIMESTAMP '2026-10-07 09:22:32' THEN '2 공개 뒤 개선 전(10/6~10/7 18:22)'
      ELSE '3 개선 뒤(10/7 18:22~)'
    END AS cohort
  FROM "User"
  WHERE nickname IS NOT NULL
    AND "signupSource" IS DISTINCT FROM 'demo'
    AND "createdAt" < (now() AT TIME ZONE 'UTC') - INTERVAL '7 days'
)
SELECT cohort,
  count(*) AS "가입",
  count(*) FILTER (WHERE EXISTS (
    SELECT 1 FROM "Todo" t WHERE t."userId" = u.id AND t."routineId" IS NULL)) AS "한번이라도_씀",
  count(*) FILTER (WHERE EXISTS (
    SELECT 1 FROM "Todo" t WHERE t."userId" = u.id AND t."routineId" IS NULL
      AND t."createdAt" < u."createdAt" + INTERVAL '7 days')) AS "7일_안에_씀"
FROM u GROUP BY cohort ORDER BY cohort;

-- 3. 재방문: 가입 다음 날부터 7일 안에 하루라도 쓴 비율(lib/metrics.ts cohortOf와 같은 정의). 창이 끝난 가입자만.
WITH u AS (
  SELECT id,
    ("createdAt" AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Seoul')::date AS joined,
    CASE WHEN "createdAt" < TIMESTAMP '2026-10-05 15:00:00' THEN '1 공개 전(~10/5)' ELSE '2 공개 뒤(10/6~)' END AS cohort
  FROM "User"
  WHERE nickname IS NOT NULL
    AND "signupSource" IS DISTINCT FROM 'demo'
    AND ("createdAt" AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Seoul')::date <= (now() AT TIME ZONE 'Asia/Seoul')::date - 8
)
SELECT cohort,
  count(*) AS "가입",
  count(*) FILTER (WHERE EXISTS (
    SELECT 1 FROM "ActiveDay" a WHERE a."userId" = u.id AND a.date BETWEEN u.joined + 1 AND u.joined + 7)) AS "7일_안에_다시_씀"
FROM u GROUP BY cohort ORDER BY cohort;
```

- 운영자 본인 계정은 빼지 않았다(지표 화면과 같다). 빼려면 `WHERE`에 운영자 id를 더한다.
- 결과를 이 문서에 옮길 때는 돌린 날짜와 함께 [측정]으로 적는다.
